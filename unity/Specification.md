# Specification.md — VPTAligned3DGS 設計書

VPT（ビデオパススルー）と 3D Gaussian Splatting（3DGS）シーンを自動で位置合わせするアプリの設計。本書は **「なぜこの方式なのか」と、そこに至るまでに何を捨てたか**を扱う。

- **どう実装されているか**（確定値・数式・データ形式）→ [`ImplementationSpec.md`](ImplementationSpec.md)
- **どう動かすか**（セットアップ・操作・実験手順）→ [`OperationGuide.md`](OperationGuide.md)
- **Unity/XR の作業規約** → リポジトリ直下 [`CLAUDE.md`](../CLAUDE.md)

> **ステータス: v7（as-built）。** 自動位置合わせまで実機で動作確認済み。
> v4 までの「オンデバイス完結・`.ply` 仮想レンダ DB・Unity Sentis 推論」志向は、実機での 3DGS×パススルー両立の難しさと計算予算から**撤回した**。撤回した設計の要約と撤回理由は §12 に残す（本文は採用した設計だけを述べる）。

---

## はじめに — このアプリは何をするか

ひとことで言うと: **「録画ずみの部屋のリアルな 3D コピー（3DGS）を、いま実際にいるその部屋に、ヘッドセット越しにピッタリ重ねて表示する」**。重ねる位置・向き・大きさを自動で合わせ、頭を動かしても貼り付いたままにする。

たとえ: 透明なフィルムに部屋を精密に描いた絵を、本物の部屋の上に寸分たがわず重ねるイメージ。本アプリはこのフィルムを置く位置・角度・拡大率を、カメラ画像から自動で計算する。

実際の流れ:

1. **歩き回る**: ユーザーが部屋の中を歩く。ヘッドセットのカメラが周囲を捉える。
2. **どこにいるか当てる**: いま見えている景色を、3DGS を作ったときの写真群（COLMAP 再構成）に照合し、**その写真群の座標系での自分の位置**を割り出す。
3. **2 つの座標系を対応づける**: 「写真群の座標系での位置」と「Quest が知っている実空間での位置」の組が複数たまると、両者を結ぶ**位置・向き・大きさの変換**が 1 つに決まる。
4. **重ねる**: その変換を 3DGS に適用する。以後はヘッドセット自身のトラッキングで貼り付いたままになる。

**鍵は 3 の「大きさ」まで一度に決まること。** 3DGS は写真から作られるため寸法が不定（何メートルの部屋かを知らない）だが、Quest 側はメートルを知っている。両者の対応から縮尺も同時に解けるので、**基準マーカーも深度スキャンも要らない。**

---

## 1. 目的とスコープ

- 作成済みの 3DGS シーンを、**それが撮影された実空間そのもの**に対して、Quest 3 のパススルー越しに自動で重ね合わせる。
- 出力は「3DGS モデル座標系 → Quest ワールド座標系」への相似変換で、`GaussianSplatRenderer` ルートの Transform（SRT）に反映する。
- **スコープ外**: 3DGS の生成（学習）、複数シーンの同時管理、動的シーンの逐次更新、毎フレームの連続追従（§13）。

---

## 2. 前提

- **同一空間への重ね合わせ**: 3DGS はユーザーが今いる実空間の再構成。すなわち再ローカライズ問題。
- **モデル側の入力**: 3DGS の `.ply` に加えて、**それを学習したときの COLMAP 再構成（`sparse/0` ＋ 元画像）をユーザーが保有していること**を前提とする。これは強い前提ではない — 3DGS を作った人は必ず COLMAP を通っているため。
- **シーン規模**: 一般的な部屋スケール。
- **照明**: 撮影時と利用時で照明が変わりうる。
- **計算配置**: 重い CV は **LAN 内の PC にオフロードする**（オンデバイス完結は目標にしない → §12）。
- **ユーザー所作**: 位置合わせのために**部屋を歩き回ることを求めてよい**。これは負担ではなく精度の源泉（§6）。
- **ワールド原点の固定**: Quest のトラッキング原点が動かないこと。動いた場合は検出して破棄する（`ImplementationSpec.md` §8）。

## 3. 問題の定式化

> 直感: 求めたいのは「3D コピー側の点に **拡大 → 回転 → 平行移動** を施して実空間の点に重ねる」その 3 操作。スケールも含めて合わせる変換を**相似変換（Sim(3)・7 自由度）**と呼ぶ。

モデル座標系 `m` → ワールド座標系 `w` への相似変換 `T_{m→w} = (s, R, t)`:

```
x_w = s · R · x_m + t
```

- **なぜ 7 自由度か**: COLMAP 由来の 3DGS はスケール不定、Quest はメートル単位。したがって `s` を推定対象に含める。
- **なぜ `s < 0` になるか**: COLMAP は右手系、Unity は左手系で、aras-p のインポータは軸を反転しない。整合には**反射**が要り、Unity の Transform では負スケールでしか表せない（§8）。
- **何を対応づけるか**: **カメラ中心**。カメラ中心は世界座標上の 1 点で、カメラ軸の向き規約（z 前方か後方か等）に依存しないので、規約の取り違えによるバグが起きない。

## 4. 利用できる入力

### 4.1 実機側（実行時）

| 入力 | 内容 | 本設計での用途 |
|---|---|---|
| ヘッドセット 6DoF 姿勢 | メートル・ワールド系 `T_{w←hmd}(t)` | 全工程の基準。貼り付きの土台 |
| パススルーカメラ画像（PCA） | `I_t`（最大 1280×960・30FPS）＋ `K` ＋フレーム姿勢 `T_{w←cam}(t)` ＋タイムスタンプ | **再ローカライズの入力**（本設計の主経路） |
| 空間アンカー | 結果の永続化 | セッション間でオーバーレイを固定 |
| Environment Depth / MRUK | 深度・床面・部屋メッシュ | **主経路では使わない。** 床スナップ（半自動）にのみ使用 |

> **OpenXR のパススルー層からはピクセルを取れない**（コンポジタに直接渡される）。画像を解析する用途には Passthrough Camera API（PCA）が必須。

### 4.2 モデル側（オフラインで用意する）

- 3DGS の `.ply`（→ `GaussianSplatAsset` に変換）。
- **COLMAP 再構成**（`sparse/0` ＋元画像）。これが再ローカライズの照合先になる。

### 4.3 姿勢とカメラの時刻整合

**姿勢は撮影時刻のものを使う。** 各フレームに付随するキャプチャ時タイムスタンプの `T_{w←cam}` を用い、フレーム到着時の最新ヘッドポーズで代用しない（エンドツーエンドで 40〜60ms の遅延があり、速い首振りでは数〜十数 px のずれになる）。

## 5. 採用した方式 — COLMAP 再ローカライズ ＋ Umeyama

### 5.1 なぜ COLMAP を照合先にするのか

自動位置合わせの本質は「いま見ている景色が、モデルのどこか」を当てることで、そのためには**照合できるデータベース**が要る。候補は 2 つあった。

| 照合先 | 長所 | 短所 |
|---|---|---|
| **COLMAP の元画像**（採用） | 実写どうしの照合なのでドメインギャップが無い。既に存在するので前処理が軽い | ユーザーが COLMAP を保持している必要がある |
| 3DGS の仮想レンダ画像 | `.ply` だけで成立する | **レンダと実写のギャップが成否を左右する**（フローター・視点依存アーティファクト・焼き込まれた照明）。DB 生成に数分〜十数分 |

**3DGS を作った人は必ず COLMAP を通っている**ので、前者の前提はほぼ無償で満たされる。一方で後者のドメインギャップは実験しないと大きさが分からないリスクだった。確実に成立するほうを採った。仮想レンダ DB は「COLMAP が無い場合の代替」に格下げした（未実装）。

### 5.2 パイプライン

```
[オフライン・シーンごとに 1 回]
  COLMAP sparse/0 + images/
    → SuperPoint 抽出 → 既存姿勢で再三角測量 → NetVLAD 大域記述子
    → 再ローカライズ DB（.ply と同じ座標系）

[オンライン・キーフレームごと]
  パススルー画像 → SuperPoint → NetVLAD で候補検索 → LightGlue でマッチ
    → 2D-3D 対応 → PnP+RANSAC → COLMAP 座標系でのカメラ中心 C_c

[集約]
  複数キーフレームの (C_c, Quest ワールドのカメラ中心 C_w)
    → Umeyama + RANSAC → Sim(3) → splatRoot へ適用
```

**なぜ hloc か**: 「大域検索 → 局所マッチ → PnP」の階層構造は再ローカライズの定番で、実装が公開されており、SuperPoint/NetVLAD/LightGlue をそのまま組み合わせられる。自前で書く理由が無い。

**なぜ再三角測量するのか**: COLMAP の元の 3D 点は SIFT で作られている。クエリ側が SuperPoint なら、DB 側の 3D 点も SuperPoint で作らないと対応が取れない。既存の**カメラ姿勢は再利用する**ので、再三角測量しても `.ply` と同じ座標系のままになる（ここがずれると全部が無意味になる）。

### 5.3 なぜ PC にオフロードするのか

SuperPoint/NetVLAD/LightGlue を Quest 3 上で回すことは検討したが、採らなかった（§12・R1）。判断の根拠:

- **描画と GPU を奪い合う。** スプラット描画は Multi-Pass でほぼ 2 倍のコストがかかっており、ここに推論を載せる余裕が読めない。
- **位置合わせは低頻度**（初期化のときだけ）なので、数百 ms の RTT を許容できる。オフロードのコストが小さい。
- **貼り付き自体はオンデバイスで完結する。** PC が切れてもオーバーレイは維持される（トラッキングは Quest 自身が担うため）。

さらに、CV を PC 側に置いたことで **hloc/pycolmap をそのまま使える**という副次的な利点が大きかった（オンデバイスなら ONNX 化・量子化・精度検証が必要だった）。

### 5.4 なぜ WSL2 を挟むのか

pycolmap が Windows ネイティブでクラッシュするため。技術的な詳細と分担は `ImplementationSpec.md` §1。

### 5.5 なぜ UDP か

低頻度の通信なので信頼性が要るなら TCP のほうが単純だが、UDP を採った理由:

1. 起動時の**ブロードキャスト・ディスカバリ**（PC の IP を手入力して再ビルドする手間を無くす）。
2. **古いリクエストを捨てて最新だけ生かす**制御がしやすい。位置合わせは最新の情報だけが要る。
3. 取りこぼしたキーフレームは**捨てて次を撮ればよい**（画像は繰り返し取れる）。再送層を実装しない判断がここで正当化される。

例外は**評価実験のイベントログ**で、これは撮り直しが効かない値（CP の実測値など）を運ぶため、後から ACK ベースの再送を足した（`ImplementationSpec.md` §9.3）。

## 6. 精度を決めるのは「どれだけ部屋を歩いたか」

本設計で最も重要な知見。**Sim(3) の残差が小さいことは、解が正しいことを意味しない。**

### 6.1 2 種類の退化

推定に使うカメラ中心の**配置**が悪いと、残差が小さいまま誤った解に落ちる。

- **共面配置＋反射の自由推定**: 3 点は必ず同一平面に乗る。反射を許すと、その平面に関する鏡映を掛けた解が**完全に同じ残差**を与えるため 2 解を区別できず、実質コインフリップになる。**頭の高さを変えずに部屋を歩くとカメラ中心はほぼ共面**なので、枚数を増やしても解決しない。
  → 対策: **反射を負に固定する。** 手性の違いは座標規約から決まる定数であって推定対象ではない（§8）。数値検証で、共面 6 点の誤り率 47%（3 点で 68%）が 0% になる。
- **共線配置**: 一直線に歩くと、その直線まわりの回転が拘束されない。反射を固定しても 100% 誤る。
  → 対策: **配置ゲート**（カメラ中心の最大間隔と第 2 主成分の広がりで弾く）。

### 6.2 ゲートは精度を上げない

閾値を締めても精度は上がらず、**ロックしなくなるだけ**だった（実測）。

| 歩き方 | ロック率 | 誤差 中央値 |
|---|---|---|
| その場で首を振る／直線 3m ／ゆるい弧 3m | 0% | — |
| 部屋を横切る（6m・弧） | 92% | 15.6 cm |
| 部屋を回る（9m・大きな弧） | 100% | 9.9 cm |

**ゲートの役割は「足りていないときに確定させない」ことだけ**で、精度の担保は**歩き方の指示**が行う。これは設計上の割り切りであり、UI（HUD の指示文）が精度の一部を担っていることを意味する。

### 6.3 確定は残差ではなく「独立な解の一致」で

**独立に解かれた 2 つの解が同じ答えに落ち着くことは、残差が小さいことよりずっと強い証拠**になる。想定していない失敗モードにも効く。一致の判定はスプラット境界ボックスの 8 隅が動く距離で行う — 位置・回転・スケールに別々の閾値を置くより「見た目がどれだけ違うか」に直結するため。閾値は `ImplementationSpec.md` §5.3。

## 7. スケールをどう確定するか

**Sim(3) の推定に含まれる `s` がそのまま答え**になる。COLMAP の任意単位と実メートルの比は、複数キーフレームの「COLMAP 座標での距離」と「Quest ワールドでの距離」の比として自動的に決まる。

- 深度センサも基準マーカーも要らない。**画像だけからメートルスケールが解ける**ことが本手法の主張の 1 つ。
- したがって**シーン固有の既知スケールを推定に注入しない**。棄却ゲートとして使う機能（`expected_scale`）はあるが既定で無効で、正しさには不要（`ImplementationSpec.md` §5.4）。**推定値が独立に実測した値とどれだけ一致したかを結果として報告する**ほうが強い主張になる。

## 8. 座標系の規約（最重要）

- **aras-p の取り込みは verbatim**: `GaussianFileReader`/`GaussianSplatAssetCreator` を確認した結果、**PLY の点座標は軸反転なしでそのまま読み込まれる**（回転だけ表示用 swizzle 補正、位置は不変）。よって **3DGS モデル座標の数値 = COLMAP 座標の数値**。
- **反射＝負スケール**: COLMAP（右手系）の数値を Unity（左手系）で解釈すると鏡像になる。整合には反射が要るが、Unity Transform は proper rotation ＋正スケールでは反射を表せないので、**一様スケールを負値**にして表現する。手動合わせでも自動推定でも `s ≈ -0.96` になる。
- **`T` は Transform にだけ適用し、スプラットデータは書き換えない。**
- **内部行列 K は正方ピクセル＋中央縦クロップ**として算出する。素朴な `fy *= h/sensorH` は誤り（`ImplementationSpec.md` §2.3）。
- 軸反転・符号操作を各所に散らさない（`CLAUDE.md` §4-4）。

## 9. 照明変化への対策

- 照合は**照明に頑健な学習特徴**（SuperPoint/NetVLAD/LightGlue）で行い、生 RGB の測光一致は使わない。
- 照合先が**実写**（COLMAP の元画像）なので、3DGS レンダに焼き込まれた照明の影響を受けない。これは §5.1 で COLMAP を選んだ副次的な利点。
- 残る限界: 撮影時と利用時で照明が大きく変わると、学習特徴でもマッチ数が落ちる。実測では品質ゲート（インライア数）が正しく弾く。

## 10. 失敗モードと対策

| 失敗モード | 対策 | 実装 |
|---|---|---|
| **カメラ中心の共面／共線配置** | 反射固定＋配置ゲート＋連続一致 | §6 |
| **Quest のワールド原点が動く** | 検出して試行を破棄・測量を無効化。残差では検出できない | `ImplementationSpec.md` §8 |
| 低テクスチャ・繰り返し模様 | 品質ゲートで棄却 → 手動フォールバック | `AlignmentManager` |

| 動的物体・人物の映り込み | RANSAC | `localize.py` |
| 対称な部屋による多解 | 複数キーフレームの一致判定 | §6.3 |
| PC が居ない／ネットワーク断 | 手動・半自動と、アンカーからの復元は動く。貼り付きはオンデバイス | §5.3 |
| 前回の解より悪い解が届く | 改悪防止ゲート | `ImplementationSpec.md` §5.3 |

## 11. 評価方法

**主結果は「収集時間 vs 精度」の 1 本の曲線。** 実機での 1 試行は「一定時間（既定 60 秒）歩き回る」だけで、曲線は保存済みキーフレームからオフラインで再構成する。

かつて E1（オーバーレイ精度）と E2（コールドスタート収束）を別モードで回していたが、**1 回の収集データから両方を出せる**ので統合した。収束時間は曲線の副産物として併記するに留める — 品質ゲートの閾値の関数でしかなく、閾値を変えれば動く数字だから。

### 11.1 指標

3DGS 上に注釈した 6 個の **Virtual CP**（モデル座標）を推定変換で写した位置と、対応する **Real CP**（実物のワールド座標）との 3D 距離を、**収集時間の関数として**出す。

```
err(t) = | T(t) · VirtualCP − RealCP |
```

**どちらの座標も `T` の推定には使っていない**ので、評価として循環していない。用語と実装は `ImplementationSpec.md` §9.1。

> **論文で書くときの但し書き**: この 6 点は推定に使わず検証にだけ使うので、写真測量の厳密な用語では control point ではなく **check point（検証点）**にあたる。実装とログでは CP の呼称を通しているが、論文本文では「6 check points (referred to as control points in the implementation)」のように一度明示する。推定に使う点と検証に使う点を取り違えられると、評価そのものが循環していると読まれかねない。

### 11.2 測定の妥当性を担保するために必要だった 5 点

いずれも実装済み。詳細は `ImplementationSpec.md` §9.5。**測定を無効にする落とし穴は、どれも「結果は出るが黙って間違う」形をしている。**

1. **コントローラ先端のピボット校正** — 未補正だと数 cm の系統誤差が全測定に乗る。校正は残差ではなく**向きの広がり**でゲートする（広がり不足だと残差が小さいまま解がずれる）。
2. **試行ごとの Quest＋PC 同時リセット** — 片方だけでは改悪防止ゲートと蓄積バッファが前試行を引きずり、試行が独立しない。
3. **評価中のアンカー永続化の無効化** — 起動時復元があると「即ロック成功」と誤記録される。
4. **`OnAutoAligned` の分離** — `OnLocked` は手動 Lock でも鳴るので収束点として使えない。
5. **ワールド原点の移動検出** — 残差にもインライア率にも現れないので、検出して破棄・無効化するしかない。

### 11.3 Virtual CP を VR 内で置き直せるようにした理由

誤差の両辺はどちらもグラウンドトゥルース側の値で、Real CP の品質には手を打ってある（上記 1・3）。一方 **Virtual CP は Editor の Scene ビューでマウス配置するだけ**で、視線方向の奥行きに歯止めが無い。その奥行き誤差は**位置合わせの性能とは無関係に報告値を悪化させる系統誤差**になる。実寸で立ち、両眼視差と運動視差を使って先端を実際にその位置へ持っていくほうが正確に置ける。

ただし 1 つだけ崩れる条件がある。

> **オーバーレイが実物に重なって見えている状態で Virtual CP を動かすと、無意識に「実物の位置」へ寄せてしまい、誤差が 0 側にバイアスする。** 答えを見ながら定規を合わせるのと同じ。

したがって編集は**位置合わせが成立していない準備段階だけ**に限り、編集中にアラインが通ったらその場で打ち切る。全編集を `aligned` フラグ付きでログし、解析スクリプトが該当セッションを警告する（先端未校正と同じ扱いで、黙って使わせない）。

## 12. 検討したが採用しなかった設計

いずれも v1〜v4 で設計まで進めたが、実装せずに撤回した。**再検討する人のために、何が理由だったかを残す。**

| 設計 | 撤回の理由 |
|---|---|
| **オンデバイス CV**（Unity Sentis で XFeat + LighterGlue、GeM 大域記述子） | 描画と GPU を奪い合い、実時間に乗るか読めなかった。位置合わせは低頻度なのでオフロードのコストが小さく、PC 側なら hloc をそのまま使える（§5.3）。Sentis に NNAPI/NPU バックエンドが無いことも判断材料 |
| **`.ply` 仮想レンダ DB**（3DGS を多数の仮想カメラからレンダして DB 化） | レンダと実写のドメインギャップ（フローター・視点依存アーティファクト・焼き込み照明）が成否を左右し、大きさが実験するまで分からない。COLMAP を前提にすれば確実に成立する（§5.1）。COLMAP が無い場合の代替として将来の選択肢に残す |
| **TCP ＋ 自作 NACK 再送層** | 画像は撮り直せるので再送が要らない。ディスカバリと「最新だけ生かす」制御のために UDP を採った（§5.5） |
| **特徴だけを送信する**（実機で抽出 → 記述子を送る） | オンデバイス推論を捨てた時点で成立しない。縮小 JPEG（長辺 512・品質 60）を送るほうが単純で、帯域も足りている |
| **Environment Depth によるスケール確定** | Sim(3) の推定に `s` が含まれるので不要（§7）。深度センサへの依存を外せたのは主張としても強い |
| **Stage C/D（ICP 精密化と毎フレーム連続追従）** | 「アンカーで貼り付き＋定期的な再ローカライズ」で実用上足りた。残差監視・ICP・one-euro フィルタは実装していない（§13） |
| **BiRP（ビルトインレンダーパイプライン）** | VR で行列周りの不具合報告があり、URP が 3DGS×Quest の定番 |
| **Single Pass Instanced** | aras-p v1.1.1 が非対応でスプラットが描画されない。Multi-Pass を採用し、その代わりスプラット数の予算を絞った |

## 13. 既知の限界と今後

- **フル連続追従は無い。** 現状は「アンカー貼り付き＋定期再ローカライズ」の軽量版。ドリフトが問題になる長時間運用では要検討。
- **PC 依存。** オンデバイス CV が無いので、自動位置合わせには LAN 内の PC が要る。
- **COLMAP 依存。** `.ply` だけでは自動位置合わせできない（仮想レンダ DB を実装すれば解消する）。
- **精度は歩き方に依存する**（§6.2）。ユーザーに歩いてもらう UI 設計が精度の一部を担っている。
- **商用化の制約**: SuperPoint と NetVLAD の公開重みは研究/非商用ライセンス（[`THIRD-PARTY-NOTICES.md`](../THIRD-PARTY-NOTICES.md)）。商用化するなら商用可のモデルへ差し替えが要る。

## 14. 用語

- **VPT**: ビデオパススルー。**3DGS**: 3D Gaussian Splatting。
- **PCA**: Passthrough Camera API（Quest 前面カメラへのアクセス）。実装は Meta XR SDK の `PassthroughCameraAccess`（MRUK v81+）。画像・K・ワールド姿勢・タイムスタンプを提供。
- **MRUK**: Meta MR Utility Kit（シーン理解：平面・メッシュ・アンカー）。
- **相似変換 / Sim(3)**: スケール付き剛体変換（7 自由度）。
- **PnP**: 2D-3D 対応からカメラ姿勢を解く。**Umeyama**: 3D-3D 対応から相似変換を解く閉形式解。
- **RANSAC**: 外れ値に頑健な当てはめ。
- **hloc**: 階層的ローカライズ（大域検索 → 局所マッチ → PnP）。
- **VPR**: Visual Place Recognition（場所認識・画像検索）。
- **SuperPoint / LightGlue / XFeat / ORB**: 局所特徴・マッチング手法。
- **NetVLAD / GeM / DBoW / SALAD**: 画像検索の大域記述子手法。
- **COLMAP**: SfM/MVS の定番実装。3DGS の学習前処理に使われる。
- **CP（Virtual CP / Real CP）**: 検証点。§11.1。
