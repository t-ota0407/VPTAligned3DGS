# Specification.md — VPTAligned3DGS

VPT（ビデオパススルー）と 3D Gaussian Splatting（3DGS）シーンを自動で位置合わせするアプリの仕様。本書は特に **位置合わせアルゴリズムの設計（なぜこの方式か・トレードオフ）** を主対象とする。Unity / XR の実装規約は `CLAUDE.md`、**実装に着手するための確定値・データ形式・疑似コード・座標数式・状態機械・テスト基準は `ImplementationSpec.md`（実装仕様書）** を参照。

> **3 文書の役割分担**: `Specification.md`（本書）＝設計の意図と選択肢。`ImplementationSpec.md`＝そのまま実装できる確定契約（既定値・型・終了条件）。`CLAUDE.md`＝Unity/XR 運用規約と最優先の前提（§0 レンダラ検証ゲート）。本書で「残課題」「方針」とした箇所は、`ImplementationSpec.md` で暫定既定値に確定済み。

> ステータス: **v6（自動位置合わせ実装完了・as-built 確定仕様）**。v4 までの「ゼロ構築・オンデバイス完結・`.ply` 仮想レンダ DB・Sentis」志向は、実機での 3DGS×パススルー両立難から撤回し、**両立済みの既存アプリ（scalabroom）をコピーして基盤に採用**、目的を**自動位置合わせ一本**に絞って実装した（写真鑑賞・拡大縮小/フェード演出は削除、アバター/IK は残置）。試行錯誤を経て**実際に動く仕様**を以下に確定する。本書 §3〜§11 はより広い設計の地図として残すが、**実装の正は下記「as-built 確定仕様」と `ImplementationSpec.md`**。
>
> **as-built 確定仕様（すべて実機動作確認済み）**:
> - **基盤/レンダラ**: scalabroom ベース。Unity 6000.3.10f1 / URP（Render Graph Compatibility Off）/ OpenXR **Multi-Pass**（aras-p v1.1.1 は SPI 非対応）/ **Vulkan** / aras-p `org.nesnausk.gaussian-splatting` v1.1.1 素 / `GaussianSplatURPFeature` を PC・Mobile 両 Renderer / フロアレベル原点。約15万スプラット `.ply`。両眼貼り付き・#151 のズレなし・ソート安定・72fps 圏内。
> - **位置合わせ方式（確定・本命）**: ユーザー保有の **COLMAP（`sparse/0`＋元画像）に対する hloc 再ローカライズ**。パススルー画像 → SuperPoint 抽出 → NetVLAD 検索 → LightGlue マッチ → `localize_sfm`(PnP) で **COLMAP=3DGS モデル座標系のカメラ姿勢** → 複数キーフレームの「カメラ中心(COLMAP)」と「Quest ワールド中心」から Umeyama で **Sim(3)** を解き、Quest の splatRoot へ適用。手動(M1)・半自動の水平/床スナップ(M2)・空間アンカー永続化(M1.5) はブートストラップ／フォールバック。`.ply` 仮想レンダ DB（§5.1）は COLMAP が無い場合の代替に格下げ。
> - **座標規約（最重要・確定）**: aras-p は PLY 点を **verbatim（軸反転なし）** で読む（`GaussianFileReader` 確認済み）。ゆえに 3DGS モデル座標の数値＝COLMAP 座標。COLMAP は右手系・Unity は左手系のため整合には **反射が必要 → splatRoot の一様スケールを負値**にして表現する（実機の手動合わせも負スケール ≈ -0.96 で成立）。Sim(3) は**カメラ中心**の Umeyama（反射許容）で解き、反射を負スケールに分解（§8）。
> - **内部行列 K**: Meta PCA は正方ピクセル。取得解像度 1280×960 は 1280×1280 センサの**中央縦クロップ**なので、画像基準 K は fx・fy を同一スケール＋中央クロップ補正で算出（PC 側 `vptserver/keyframe.py: k_for_image_from_meta`）。
> - **計算配置（確定）**: 重い CV は **WSL2(Ubuntu)+CUDA で実行**する（pycolmap は Windows ネイティブで `reconstruction.rigs` アクセス時にクラッシュ。Linux で安定）。UDP 受信・Sim(3) 返送・GUI は **Windows の `run.py`**。両者は **共有フォルダ（`/mnt/c`）経由で疎結合**（run.py がセッションフォルダ・cv.json・キーフレームを書き、WSL2 の localize が読み、Sim(3) を `result_sim3.json` に書き、run.py が Quest へ返送）。貼り付き描画・アンカー永続化はオンデバイス。
> - **通信（実装済みの形）**: UDP ベストエフォート。13B ヘッダ ＋ ペイロード（type=1 META(JSON)・type=2 IMG(JPEG チャンク)・**type=3 RESULT(Sim(3) JSON, PC→Quest)**）。ポート: データ **50000** / ビーコン **50001**（PC→LAN, Quest が送信元 IP を自動学習）/ 結果 **50002**（PC→Quest）。実機は**特徴ではなく縮小 JPEG**を送り PC が全 CV を行う簡素版（NACK 再送は将来課題）。AP がブロードキャストを遮断する環境では自動検出不可 → `manualIPAddress` 固定（ユニキャストは通る）。ビーコン受信に `CHANGE_WIFI_MULTICAST_STATE` 権限。

> - **実装状況（as-built・すべて実機確認済み）**: M1 手動合わせ / M1.5 アンカー永続化 / M2 半自動（水平化＋床スナップ）/ M3（カメラ取得・キーフレームオフロード・COLMAP 再ローカライズ・Sim(3)・Quest 返送・splatRoot 適用）に加え、堅牢化フェーズ完了:

## はじめに — このアプリは何をするか（初めて読む人向け）

ひとことで言うと: **「録画ずみの部屋のリアルな 3D コピー（3DGS）を、いま実際にいるその部屋に、ヘッドセット越しにピッタリ重ねて表示する」** アプリ。重ねる位置・向き・大きさを自動で合わせ、頭を動かしても**貼り付いたまま**にする。

たとえ: 透明なフィルムに部屋を精密に描いた絵を、本物の部屋の上に寸分たがわず重ねるイメージ。本アプリは、このフィルムを置く位置・角度・拡大率をセンサとカメラから**自動で計算し続ける**。

実際の動き（専門用語なしの流れ）:
1. **起動・見回し**: ユーザーが数秒ゆっくり首を振る。ヘッドセットのカメラと深度センサが周囲を捉える。
2. **大まかに合わせる（初期化）**: いま見えている景色と、3D コピーを仮想的に撮った画像を照合し、置く位置・向き・大きさを推定する。
3. **精密に合わせる**: 形（深度）と見た目（画像）のズレを最小化し、誤差を数 cm／数 px 以下に追い込む。
4. **貼り付け続ける（追従）**: 以後はヘッドセットの自前トラッキングで貼り付けたまま、わずかなズレだけを継続補正する。ズレが大きくなったら 2 に戻る。

重い計算（初期化）は必要なら LAN 内の PC に肩代わりさせられるが、**貼り付き自体は常にヘッドセット単体で動く**ので、PC が切れてもオーバーレイは維持される。

**この文書の読み方（読者タイプ別）**:
- 全体像だけ知りたい → この「はじめに」＋ §1（目的）＋ §6 冒頭のパイプライン図。
- アルゴリズムの核を読む → §5（方針）→ §6（各段の中身）→ §7（スケール）。
- 実装の前提・制約を確認する → §2・§4。**ただし最優先の前提は `CLAUDE.md` §0（レンダラ実機検証ゲート）**。
- **記号・略語（Sim(3) / PnP / ICP / hloc / VPR / RANSAC など）は §13 の用語集にまとめてある。** 初見の語が出たら §13 を見てから戻ると速い。

## 1. 目的とスコープ

- 作成済みの 3DGS シーンを、**それが撮影された実空間そのもの**に対して、Meta Quest 3 のパススルー越しに**自動で厳密に重ね合わせる**。
- 出力は「3DGS モデル座標系 → Quest ワールド座標系」への変換であり、`GaussianSplatRenderer` ルートの Transform（SRT）に反映してオーバーレイを実現する。
- 位置合わせは一度きりで終えず、**リアルタイムに連続して追従・微調整**する。
- スコープ外（現段階）: 3DGS の生成（学習）、複数シーンの同時管理、動的シーンの逐次更新。

---

## 2. 前提・確定事項

- **同一空間への重ね合わせ**: 3DGS はユーザーが今いる実空間の再構成（=リローカライズ問題）。
- **入力データの層構造（モデル側）**:
  - 基本線（必達）: 入力は `.ply`（→ GaussianSplatAsset）**のみ**でも動作。
  - 強化（任意）: COLMAP のカメラ姿勢・疎な 3D 点・元画像があれば使用。
- **ランタイムセンサ依存（実機側、モデル側とは独立）**: **Environment Depth と MRUK を前提にしてよい**。利用不可時は縮退動作。
- **シーン規模 / 精度**: 一般的な部屋スケール。要求精度は可能な限り高い。目標 **3D RMSE 数 cm 以下／再投影 数 px 以下**。
- **照明**: 撮影時と利用時で照明が変わりうる前提。照明変化に頑健な手法を優先。
- **計算配置**: **Quest 3 オンデバイス完結が第一目標**。必要に応じ **UDP で GPU 搭載 PC にオフロード**可。
- **ユーザー所作**: コールドスタート時に**数秒の見回し**を求めてよい。
- **連続性**: 確定後もロックしたまま**リアルタイム連続追従・微調整**を行う。

## 3. 問題の定式化

> 直感: 求めたいのは「3D コピー側の点に **拡大 → 回転 → 平行移動** を施して、実空間の点にピッタリ重ねる」その 3 操作。下式の `s`（拡大率）・`R`（回転）・`t`（平行移動）がそれにあたる。スケールも含めて合わせる変換を **相似変換（Sim(3)・7自由度）** と呼ぶ（→ §13）。

モデル座標系 `m` → ワールド座標系 `w` への**相似変換** `T_{m→w} = (s, R, t)`:

```
x_w = s · R · x_m + t      （s>0: スケール, R∈SO(3): 回転, t∈ℝ³: 並進）
```

- **相似変換（7自由度）**: COLMAP 由来の 3DGS はスケール不定、Quest はメートル単位のため `s` を含めて推定（§7）。
- **重力事前拘束**: モデル側の床面・重力上方向を推定し、回転 2 自由度を事前固定 → 残りは **ヨー＋水平並進(2)＋スケール**。
- **精度目標**: 最終段の測光/特徴 render-and-compare（§6 Stage C）で再投影をサブピクセル〜数 px に追い込む。Quest の自前トラッキングが安定なため、初期確定後の連続追従は**残差ドリフト補正**が主目的。

## 4. 利用可能な入力

### 4.1 Quest 実機側（実行時）
| 入力 | 内容 | 用途 |
|---|---|---|
| ヘッドセット 6DoF 姿勢 | メートル・ワールド系 `T_{w←hmd}(t)` | 全工程の基準・追従の土台 |
| パススルーカメラ画像 (PCA) | `I_t`（最大 1280×960・**30FPS**）＋内部パラメータ `K`＋フレーム姿勢 `T_{w←cam}(t)`＋タイムスタンプ。**両眼同時取得可** | 外観ベースのリローカライズ／検証。レート/レイテンシ/同期は §4.3 |
| Environment Depth | **深度センサ視点**のメートル深度（毎フレーム）。PCA-RGB とは視点が異なり、画素対応には再投影が必要（§8） | 幾何レジストレーション・**スケール確定**・遮蔽 |
| MRUK シーン | 床・壁・天井平面、部屋メッシュ、アンカー | 重力・床面の事前情報、粗い幾何 |
| 空間アンカー | 結果の永続化 | セッション間でオーバーレイ固定 |

> **多視点の取り方**: PCA は両眼同時取得が可能なので、(a) 左右カメラの**固定基線ステレオ**で 1 フレームから初期スケールを得る経路と、(b) ヘッドセット移動に伴う**モーションステレオ**の両方を使える。(a) は短時間でスケールを与えられるがベースラインが短く遠距離は不正確、(b) はベースラインを稼げるが並進所作が要る（§6.1）。既定は Environment Depth 優先（§7）とし、(a)(b) は補完・検証に用いる。

### 4.2 モデル側（オフライン前処理で生成）
- 基本線（`.ply`）: スプラット中心点群 `P_m`（色・スケール・不透明度・法線付き）、床面/重力上方向、**多視点仮想レンダリングのローカライズ DB**（§5.1）。
- 強化（COLMAP・元画像）: 元画像＋姿勢＋疎な 3D 点を、より忠実な DB として利用。

### 4.3 PCA のレート・レイテンシ・姿勢同期（精度の前提）
目標精度（再投影 数px〜サブピクセル）はカメラと姿勢の**時刻整合**に直接依存するため、ここを曖昧にしない。

- **実測前提値**: 解像度 最大 1280×960、**30FPS**、エンドツーエンド・レイテンシ **約 40〜60ms**。クエリ推論時は長辺 〜512px へダウンスケール（§5.3）。
- **姿勢は撮影時刻のものを使う**: 各フレームに付随する**キャプチャ時タイムスタンプ**の `T_{w←cam}` を用いる。フレーム到着時の最新ヘッドポーズで代用しない（40〜60ms 分の動き＝速い首振りで数〜十数 px のずれになる）。タイムスタンプが取れない経路では使用フレームを静止時に限定する。
- **追従層との整合**: 追従は 5〜15Hz（§5.5）だが PCA は 30FPS・遅延ありなので、CV 結果は**撮影時刻に紐付けて過去姿勢に適用 → 現在時刻へ前方補正**してからオーバーレイ `T` に反映する。描画スレッド（72/90Hz）は CV を待たず最新ヘッドポーズで貼り続ける。
- **品質ゲート**: モーションブラー（IMU 角速度）と露出/明るさでフレームを採否（§6.1）。

## 5. アーキテクチャ方針

### 5.1 `.ply` 基本線を成立させる中核アイデア
前処理で 3DGS を多数の仮想カメラからレンダリングし、各レンダ画像から局所特徴と大域記述子を抽出。各特徴点はレンダ深度で 3D モデル点に逆投影しておく。これで `.ply` だけから「画像検索 → 2D-2D マッチ → 2D-3D 対応 → PnP」（hloc 流）が成立する。元画像がある場合は実画像 DB に差し替え（外観ギャップ低減）。

**仮想カメラ配置（DB 生成の設計）**:
- **配置領域**: 床面（§3 で推定）から **目線高さ 1.2〜1.7m** の帯に、部屋の歩行可能領域をグリッド状に配置（例: 水平 0.5〜1.0m 間隔）。各位置で**ヨーを 30〜45° 刻み**に回す。スプラット密度がほぼ 0 の場所（=壁の外・物体内部）はレンダ深度・不透明度から検出して**除外**し、壁内部からの無効ビューを作らない。
- **画角/解像度**: PCA に近い内部パラメータ（画角・アスペクト）で生成し、実機クエリとの視点差を縮める。
- **規模/前処理時間**: キーフレーム数は数百〜数千（§5.3）。生成は Editor/Python のオフライン一括処理で、所要時間とサイズを Editor 上に表示。部屋スケールで数分〜十数分を目安に、配置間隔で調整。
- **DB 品質ゲート**: 各レンダの特徴点数・有効深度割合が閾値未満のビューは破棄。

**レンダ vs 実画像のドメインギャップ（照明とは別問題）**: 3DGS レンダには**フローター・視点依存アーティファクト・ベイクされた照明**があり、実パススルーとの特徴マッチを劣化させる。対策として、(a) アーティファクトの多い領域（不透明度低・スケール過大ガウシアン）をマスク、(b) 照明不変表現での記述（§9）、(c) 元画像が使える強化モードでは実画像 DB を優先（§4.2）。**このギャップが基本線の成否を左右する**ため、検証指標（インライア率・成功率）で常時監視する。

### 5.2 計算配置の全体方針（二層分離）
処理を**重さと頻度**で二層に分ける。
- **連続追従層（必ずオンデバイス・高頻度）**: 姿勢予測＋軽量 ICP＋疎特徴トラッキング。ネットワーク非依存でリアルタイム性を担保。
- **大域ローカライズ層（重い・低頻度: 初期化と復帰時のみ）**: 特徴抽出・検索・マッチ・PnP・相似変換。オンデバイス（軽量モデル）または **UDP で PC にオフロード**。

### 5.3 特徴抽出・マッチングのモデル選定（残課題①）
照明頑健性・推論コスト・マッチ精度のバランスで選ぶ。すべて Editor 側 DB 構築と実機側クエリで**同一手法に揃える**こと。

局所特徴（キーポイント＋記述子）:
| 経路 | 採用 | 理由 |
|---|---|---|
| オンデバイス主 | **XFeat（+ 軽量マッチャ LighterGlue）** | モバイル/CPU でも高速。学習特徴で照明・視点変化に頑健 |
| オンデバイス・フォールバック | **ORB** | NN 推論不要・極軽量。Depth/幾何ルート併用時の最低保証 |
| PC オフロード時 | **SuperPoint + LightGlue** | 最高精度。実機外なので計算コストを許容 |

大域記述子（画像検索/場所認識, VPR）:
- オンデバイス: **DBoW（ORB の Bag-of-Words）** か小型 **GeM プーリング**記述子。DB は前処理で固定（数百〜数千キーフレーム）なので、コンパクト記述子の総当たりコサインで十分。
- PC: **NetVLAD / SALAD** 等の高精度 VPR。

ランタイム/実装:
- モデルは ONNX 化し **Unity Sentis（現 Unity Inference Engine）** で実行。Sentis のバックエンドは **CPU / GPU(Compute)** で、**NNAPI/NPU バックエンドは無い**（Quest はアプリから NNAPI/NPU に実質アクセス不可）。量子化は Sentis の **FP16 / Uint8** を使用（外部 INT8 ONNX の取り込みは現状未対応）。GPU 実行は描画（スプラットレンダ）と GPU 時間を奪い合う点に注意し、レート分離（§5.5）で吸収する。
- **実機推論コストは未検証**。XFeat(+LighterGlue) と VPR 記述子が大域ローカライズの低頻度予算に乗るかを §0 検証後に Sentis で実測し、乗らなければ UDP オフロード既定に切替（残課題③）。
- クエリ入力は長辺 〜512px 程度にダウンスケールして推論コストを抑制。
- DB は GaussianSplatAsset の傍らに格納。記述子次元・キーフレーム数・**メモリ上限**を Editor で設定可能にする（→ §5.6 メモリ予算）。

### 5.4 UDP オフロード・プロトコル（残課題②）
> **v5 注記（実装済みの形が正）**: 以下は「特徴を送り NACK 再送」を含む将来設計。**現行実装はより簡素**で、(1) PC が存在通知ビーコン（UDP 50001, `"VPTSRV1"`＋データポート）を周期送信 → Quest が送信先 IP を自動学習（手動指定も可）、(2) キーフレームは **13B ヘッダ ＋ ペイロード**（`['V','P', type, reqId(4 LE), idx(2 LE), total(2 LE), len(2 LE)]`、type=1=META(UTF-8 JSON: w,h,sw,sh,fx,fy,cx,cy,px..qw,ts,n,len)、type=2=IMG(JPEG チャンク, 既定 1100B)）を **UDP 50000** へベストエフォート送信、(3) **特徴ではなく縮小 JPEG**（長辺 512・品質 60）を送り PC 側で全 CV を行う、(4) 取りこぼしたキーフレームは破棄して再キャプチャ（NACK 再送は未実装）。実装は Quest 側 `KeyframeUploader.cs`/`UDPManager.cs`、PC 側 `server/`（`vptserver/`：protocol/reassembler/udp_receiver/keyframe/storage/beacon＋run.py）。Sim(3) 返送は M3 ステップ3 で追加する。

大域ローカライズのみ PC に委譲。**生画像ではなく実機抽出済みの特徴**を送り、PC が検索・マッチ・PnP・相似変換を解いて Sim(3) を返す。

> **UDP か TCP か**: 大域ローカライズは低頻度（初期化/復帰時のみ）なので、信頼性が要るなら **TCP の方が実装が単純**で、以下の自作再送層は不要になる。UDP を採るのは (1) 起動時のブロードキャスト・ディスカバリ、(2) 古いリクエストを捨てて最新だけ生かす制御がしやすい、(3) 研究用に挙動を細かく観測したい、の 3 点が主目的。**これらが不要なら TCP を既定にしてよい**（要確認）。以下は UDP を採る場合の設計。

ペイロード設計:
- リクエスト（実機→PC, 大）: キーフレームごとに「キーポイント座標＋記述子（int8）＋大域記述子＋内部パラメータ `K`＋ワールド姿勢 `T_{w←cam}`」。1 キーフレーム ≈ 1024 点 ×（座標 + 64次元 int8 記述子）≈ 70KB 前後。k=3〜8 枚で数百 KB。必要なら検証用に低解像度 JPEG を併送。
- レスポンス（PC→実機, 小）: `Sim(3)`（s,R,t）＋インライア数＋信頼度。1 データグラムに収まる（数十バイト）。

データグラム/分割:
- アプリ層ペイロードは **≤ 約 1200 バイト**に分割し IP フラグメンテーションを回避。
- ヘッダ例（計 18B）: `magic(2) | version(1) | msg_type(1) | request_id(4) | chunk_index(2) | total_chunks(2) | payload_len(2) | crc32(4)`。

信頼性（アプリ層）:
- **選択的再送（NACK 方式）**: 実機が全チャンク送信 → PC が欠落チャンク番号を NACK で返す → 実機が欠落分のみ再送 → 全受信 or タイムアウトまで反復。
- レスポンスは小さく、来なければ実機がリクエストを再送（PC は `request_id` で重複排除）。
- **タイムアウト/バックオフ**: RTO 初期 50〜100ms・指数バックオフ・最大再送回数を設定。リクエスト全体のタイムアウト 1〜2s で打ち切り、オンデバイス/ハイブリッドへフォールバック。
- 順不同・重複は `chunk_index` で再構成・破棄。古い `request_id` は無視。

運用:
- 大域ローカライズは低頻度のため数百 ms の RTT を許容。**追従はオンデバイス完結**で、PC 断でもオーバーレイ維持。
- PC アドレスは設定値、または起動時の UDP ブロードキャストでディスカバリ。
- **LAN 内利用前提・非暗号化**（研究用途）。必要なら暗号化/認証を追加。

メッセージ種別:
| msg_type | 方向 | 内容 |
|---|---|---|
| `LOC_REQ` | 実機→PC | キーフレーム特徴一式（分割） |
| `LOC_NACK` | PC→実機 | 欠落チャンク番号 |
| `LOC_RESP` | PC→実機 | Sim(3) + 信頼度 |
| `PING/PONG` | 双方向 | ディスカバリ・死活監視 |

### 5.5 連続追従の計算予算とレート設計（残課題③）
Quest 3（Snapdragon XR2 Gen 2）。**処理ごとにレートを分離**し、描画と競合させない。
| 処理 | レート（初期値） | 配置 | 役割 |
|---|---|---|---|
| オーバーレイ描画 | ディスプレイレート（72/90Hz） | 描画スレッド | Quest 姿勢＋現在 `T` で変換するだけ（CV 不要、ここが貼り付きを担保） |
| 追従・微調整 | 5〜15Hz（適応） | 別スレッド/非同期 | 残差ドリフトの継続補正（軽量 ICP＋疎特徴トラッキング） |
| 大域ローカライズ | オンデマンド（初期化/復帰） | オンデバイス or PC | `T` の初期化・大ドリフト時の復帰 |

予算とデグレード方針:
- 追従 1 サイクルの CV コスト上限の目安 〜数 ms。ICP は**ダウンサンプル点群 2〜5k 点**で point-to-plane を 1〜3 反復（インクリメンタル）。疎特徴トラッキングは KLT 等で **200〜500 点**。
- `T` 更新は**スムージング（one-euro / 指数フィルタ）**で適用しジッタを防ぐ。サイクルが予算超過なら**スキップ**（描画は継続）。
- **サーマル適応**: 残差が小さい/発熱時は追従レートを下げる。描画（スプラット 〜40 万で 72fps の目安, CLAUDE.md §4-3。ただし VR ステレオ・Render Mode 依存で目安は変動）を最優先。

### 5.6 メモリ予算（オンデバイス）
Quest 3 は共有メモリで、GaussianSplatAsset・レジストレーション資産・推論モデルが同居する。上限を超えると OOM やスワップで描画が破綻するため、Editor で各サイズを表示し合算をチェックする。
- **内訳（要実測）**: (a) GaussianSplatAsset（品質レベル依存・支配的）、(b) ローカライズ DB（大域記述子＋局所記述子＋逆投影 3D 点。例: 1000 キーフレーム × 1024 点 × 64次元 int8 ≈ 65MB ＋座標・大域記述子）、(c) ICP 用ダウンサンプル点群 `P_m`、(d) Sentis モデル（量子化後）、(e) ランタイム作業領域。
- **方針**: DB のキーフレーム数・記述子次元・点群解像度で総量を調整。上限超過時は品質レベル↓／DB 間引き／点群間引きの順に削る（CLAUDE.md §4-3 の予算と整合）。

## 6. アルゴリズム全体パイプライン

> 「はじめに」の 4 ステップとの対応: **A** が事前準備、**B** が「②大まかに合わせる」、**C** が「③精密に合わせる」、**D** が「④貼り付け続ける」、**E** は B が失敗したときの手動の助け舟、**F** は結果の保存と見張り。

```
[A] 前処理(オフライン)
      → [B] 大域ローカライズ(初期化・復帰)
      → [C] 精密化(初期 refine)
      → [D] 連続追従(リアルタイム微調整)  ←→ ドリフト検出時は [B] へ復帰
 [E] ハイブリッド/手動フォールバック（Bが失敗/低信頼）
 [F] ロック・永続化・監視
```

### Stage A — 前処理（Unity Editor / Python、オフライン）
1. `.ply` → GaussianSplatAsset 変換。
2. レジストレーション資産生成: 点群 `P_m`（法線付き）／重力上方向・床面／ローカライズ DB（基本線=レンダ由来 2D-3D マップ、強化=COLMAP）。採用特徴は §5.3 に統一。
3. GaussianSplatAsset の傍らにサイドファイルとして格納。

### Stage B — 大域ローカライズ（初期化・復帰、自動）
1. 数秒の見回し中に既知ワールド姿勢付きキーフレームを k 枚取得（§6.1）。
2. **重力事前整合**で回転をヨーのみに縮約。
3. 2 ルート併用・融合:
   - **外観ルート**: 大域記述子検索 → 局所特徴マッチ → ライブ 2D ↔ モデル 3D → PnP+RANSAC で `T_{m←cam}` → 既知 `T_{w←cam}` と合成。複数フレームの **3D-3D 対応**を Umeyama+RANSAC で相似変換化（**スケール確定**）。
   - **幾何ルート（低テクスチャ・照明変化に強い）**: Environment Depth/MRUK のライブ点群を**床面上 2D（ヨー＋xy＋スケール）**へ縮約 → 2D 相関/分枝限定で粗合わせ。
4. **仮説検証**: レンダ vs ライブの特徴インライア数・深度整合（照明非依存指標が主、測光は従）で評価、閾値で成功/失敗。

### Stage C — 精密化（初期 refine、一度きり）
1. **幾何 ICP**（point-to-plane）: B のスケールを初期値に 7 自由度（scaled-ICP）/6 自由度を最適化。
2. **測光/特徴 render-and-compare**: 特徴再投影誤差（照明頑健）を主・測光を従に Sim(3) 上で Gauss-Newton/LM。サブピクセルを狙う。

### Stage D — 連続追従（リアルタイム微調整）
- §5.5 のレート/予算でオンデバイス実行。残差を監視し閾値超過で Stage B（復帰）。

### Stage E — ハイブリッド / 手動フォールバック
- B が失敗/低信頼時、ハンドジェスチャで粗配置・スケール → C/D の同一バックエンドでスナップ。対称な部屋・極端な低テクスチャのブートストラップにも使用。

### Stage F — ロック・永続化・監視
- 確定 `T` を空間アンカーに保存しセッション間で復元。残差監視でドリフト検出 → 再ローカライズ。
- **アンカー自体のドリフト対策**: 空間アンカーはトラッキングの再ローカライズで**自身が補正されて動く**ことがある。`T` は**アンカーのワールド姿勢に相対**で保持し（絶対ワールド座標で焼き込まない）、アンカー更新イベントに追従させる。複数アンカーに冗長保存し、整合が取れないアンカーは破棄。アンカーのリローカライズに失敗した場合は Stage B（大域ローカライズ）へ戻る。

### 6.1 見回し所作・キーフレーム選択・三角測量（残課題④）
- **所作**: 緩やかに首を振り（水平 30〜60° を 3〜5 秒）シーンを覆う。**純回転は避け、わずかに並進（ストレイフ）を促す**。Environment Depth があれば純回転でもメートル点が得られるが、単眼三角測量のフォールバックには並進が必須。
- **キーフレーム選択**: 前キーフレームから **回転 ≥ 約 10°** または **並進 ≥ 約 15cm** で新規採用。**モーションブラー**（IMU 角速度閾値）と**露出/明るさ**（PCA の輝度推定）で品質ゲート。k=3〜8 枚。
- **三角測量フォールバックの最小ベースライン**: 累積並進 ≥ 約 20〜30cm かつ**パララックス角 ≥ 約 3°**を満たすまでスケールを信頼しない。満たすまでは Environment Depth のメートル深度を優先（既定）。
- 数値はすべて初期値。実測で調整する。

## 7. スケールの確定方法

優先順:
1. **Environment Depth のメートル 3D-3D（既定・最優先）**。`.ply` のみで成立し高精度。
2. 既知メートル基線の多視点三角測量（§6.1 の最小ベースライン条件）。
3. MRUK の床・部屋寸法など既知幾何。
4. （任意・将来）既知サイズの基準マーカー。

## 8. 座標系変換の規約

- **aras-p の取り込みは verbatim（確定・最重要）**: `GaussianFileReader`/`GaussianSplatAssetCreator` を確認した結果、**PLY の点座標は軸反転なしでそのまま読み込まれる**（回転だけ表示用 swizzle 補正、位置は不変）。よって **3DGS モデル座標 `m` の数値 = COLMAP 座標 `c` の数値**。`T` は `GaussianSplatRenderer` ルートの Transform（SRT）に適用し、**スプラットデータは書き換えない**。
- **反射＝負スケール（確定）**: COLMAP `c` は右手系、Unity world `w` は左手系。右手系の数値を左手系で解釈すると鏡像になるため、`m`→`w` の整合には**反射**が要る。Unity Transform の proper rotation＋正スケールでは反射を表せないので、**一様スケールを負値**にして反射を表現する（負スケール＝原点対称の鏡映）。実機の手動合わせも負スケール（≈ -0.96）で成立しており、自動推定の Sim(3) も負スケールになる。`solve_sim3` は反射を許す Umeyama で当てはめ、`det(Q)<0` のとき `scale=-s, R=-Q`（det +1）に分解して splatRoot に渡す（`vptserver/cv/geometry.py`）。
- 軸反転・スケール係数などの規約値は一箇所に集約し根拠をコメント（CLAUDE.md §4-4 / §10）。
- **PCA-RGB と Environment Depth の整合**: 深度は深度センサ視点、RGB は前面カラーカメラ視点で**光学中心が異なる**。RGB 画素に深度を付与する／深度点を RGB 特徴と対応づける際は、各々のワールド姿勢 `T_{w←cam}` を用いて**一方の視点へ再投影**する。視点差・遮蔽で対応が取れない画素は破棄。この再投影誤差が幾何ルートのスケール確定精度に効くため、規約として明記する。
- **内部行列 K の解像度規約（確定）**: Meta PassthroughCameraAccess は**正方ピクセル**（`Intrinsics.FocalLength.x == .y`）。`Intrinsics.SensorResolution`（例 1280×1280）と実際に取得する `CurrentResolution`（例 1280×960）は一致しないことがあり、低い方は**センサを中央で縦クロップ（垂直 FOV を狭めた）した**もの（公式ドキュメント: 1280×1280 は「垂直 FOV を拡張」）。クロップは焦点距離[px]を変えないため、**素朴な `fy *= h/sensorH` は誤り**（縦を不当に縮める）。送信画像(w,h)に対応する K は次で算出する: 非クロップ軸（画像とセンサのアスペクト比較で決まる）から一様スケール `scale` を取り、`fx,fy *= scale`（同一）、`cx,cy` は中央クロップのオフセットを引いてから `*= scale`。この計算は PC 側 `vptserver/keyframe.py: K_for_image()` に実装。最終的な妥当性は Stage B の PnP 再投影誤差で検証する（誤った K なら誤差が大きく出る）。

## 9. 照明変化への対策

- 大域ローカライズ・検証は**照明頑健な学習特徴**を主軸、生 RGB の測光一致は補助。
- スプラットレンダは照明が焼き込まれるため、live との測光残差は信頼度を下げ、**特徴再投影・幾何/深度残差を優先**。
- 強化モードで元画像が使えるならレンダより実画像 DB を優先。
- 必要に応じエッジ/勾配などの**照明不変表現**で残差評価。

## 10. 失敗モードと対策

| 失敗モード | 対策 |
|---|---|
| 低テクスチャ・繰り返し模様 | 幾何ルート優先、手動フォールバック、重力＋床面拘束 |
| 照明変化による外観ギャップ | 照明不変特徴、幾何/深度ルート、強化モードの実画像 DB（§9） |
| 動的物体・人物の映り込み | RANSAC、領域マスキング |
| 対称な部屋による多解 | 多視点による曖昧性解消、重力＋床面拘束 |
| Quest 深度の遠距離ノイズ・細構造 | point-to-plane、外れ値除去、近距離優先 |
| Environment Depth/MRUK 利用不可 | 縮退（外観ルート＋手動初期化、スケールは三角測量） |
| 純回転で三角測量が縮退 | 並進を促す所作、Environment Depth 優先（§6.1） |
| コールドスタート失敗 | 信頼度閾値で検知 → ハイブリッドへ自動移行 |
| PC オフロードのネットワーク断 | 追従はオンデバイス継続、大域のみ一時停止 |

## 11. 評価方法・指標

> **as-built（実装済み・論文対応）**: 下記の候補指標のうち、投稿論文で実施するのは**「収集時間 vs 精度」の 1 本の曲線**に統一した。実装は `Assets/Scripts/Experiment/`、集計は `server/analysis/experiment_report.py`（主結果）と `analyze_experiments.py`（実測の健全性・収束の要約）、運用手順は `readme.md` §9。
>
> **用語（Virtual CP / Real CP）**: `CP_01` … `CP_06` は**実在する 1 つの物理的特徴**を指すが、記録する座標は 2 つある。混同を避けるため呼び分ける。
>
> | 呼び方 | 何の座標か | どこで決めるか | ログ名 |
> |---|---|---|---|
> | **Virtual CP** | 3DGS モデル座標（splatRoot ローカル）| Unity Editor（`ControlPointToolWindow`）、または VR 内の `ControlPointEdit` | `cp_model_edit` |
> | **Real CP** | 同じ特徴の**実物**のワールド座標 | VR 内の `ControlPointMeasure`（校正済みコントローラ先端で実物に触る）| `cp_survey` |
>
> 呼び分けは **HUD・ワールドのラベル・文書の文言だけ**で、クラス名・UDP イベント名・JSON の鍵は従来のまま（過去ログと解析スクリプトの互換のため）。実機の画面に出る名前は `VCP_01` / `RCP_01`（球＝model 側 / 橙の点＝実測値）で、**同じ点の 2 つの側を色ではなく文字で見分けられる**ようにしてある。
>
> **論文で書くときの但し書き**: この 6 点は相似変換の推定には一切使わず検証にだけ使うので、写真測量の厳密な用語では control point ではなく **check point（検証点）** にあたる。実装・ログでは CP の呼称を通しているが、論文本文では「6 check points (referred to as control points in the implementation)」のように一度明示する。推定に使う点と検証に使う点を取り違えられると、評価そのものが循環していると読まれかねないため。
>
> - **指標**: 3DGS 上に注釈した 6 個の Virtual CP を推定相似変換で写した位置と、対応する Real CP との 3D 距離（平均/中央値/最大）。すなわち `err = |T(Virtual CP) − Real CP|` を**収集時間の関数として**出す。**どちらの座標も `T` の推定には使っていない**ので評価として成立する。
> - **測り方**: 実機での 1 試行は「一定時間（既定 60 秒）歩き回ってキーフレームを送る」だけ。曲線は保存済みキーフレームから**時刻ごとに姿勢を解き直して**オフラインで再構成する。かつて E1（精度）と E2（コールドスタート収束）を別モードで回していたが、1 回の収集データから両方を出せるので統合した。収束時間（最初のキーフレーム送信 → 最初の自動ロック）は曲線の副産物として併記するに留める — 品質ゲートの閾値の関数でしかなく、閾値を変えれば動く数字だから。
> - **CP の扱い**: Virtual CP は Editor で 1 回置いて固定、Real CP は**実験前に 1 回だけ実測**する。誤差の両辺はどちらも試行不変なので、試行ごとに測り直す意味が無い（測り間違いの機会が増えるだけ）。前提は「Quest のワールド原点が動かないこと」で、動いた場合は Real CP を自動的に無効化する。
>
> **Virtual CP の VR 内修正（`ControlPointEdit`・位置合わせ前のみ）**: 誤差の両辺はどちらもグラウンドトゥルース側の値で、Real CP の品質には手を打ってある（先端校正・移動量ゲート・原点移動の検出）。一方 Virtual CP は **Editor の Scene ビューでマウス配置するだけ**で、視線方向の奥行きに対する歯止めが無い。マウス配置の奥行き誤差はそのまま**系統誤差として報告値に乗る**ので、先端未校正と同種の問題になる。実寸で立ち、両眼視差と運動視差を使って**先端を実際にその位置へ持っていく**ほうが奥行きが取れるので、VR 内で置き直せるようにした（位置合わせ前でもスティックでシーンを手の届く位置へ寄せられる = `PoseControlMode.SticksOnly`）。
>
> Virtual CP は **T の推定に一切使っていない注釈**なので、**モデルだけを見て**決める限り評価は成立する。崩れるのは 1 つだけ ——
>
> > **オーバーレイが実物に重なって見えている状態で Virtual CP を動かすと、無意識に「実物の位置」へ寄せてしまい、誤差が 0 側にバイアスする。** 答えを見ながら定規を合わせるのと同じ。
>
> したがって編集は **`HasAcceptedSim3` でも `Locked` でもない準備段階だけ**に限る（試行中も不可。編集中に Sim(3) が返って適用されたらその場で打ち切る）。加えて、解析は Virtual CP を `cp_survey` イベントに載った**記録時点のスナップショット**から取るので（`server/analysis/experiment_report.py`）、Real CP を測ったあとに編集するとシーンとログが黙って食い違う。だから**編集したら Real CP を無効化して測り直させる**。全編集は `aligned` フラグ付きでログに残り、`analyze_experiments.py` が「アライン済みで編集した／実測後に編集して測り直していない」ログを警告する（先端未校正と同じ扱いで、黙って使わせない）。
>
> **スプラットの表示は「いま何を見る作業か」で決まる**: Virtual CP の編集は**モデルを見る**作業なので開始時にスプラットを表示し、Real CP の測定は**実環境を見る**作業なので開始時に非表示にする（試行の収集中と同じ扱い）。測定中に位置合わせ前のスプラットが出ていると、先端を当てたい実物そのものを覆い隠すため、これは見た目ではなく**測定精度**の問題。ただし CP の球・ラベル・記録済みの点はこの 2 局面ではスプラットに連動させない（消すと「次はどの点か」の案内が失われる）。詳細は `readme.md` §5-3。
>
> **測定の妥当性を担保するために必要だった 5 点**（いずれも実装済み。詳細は `CLAUDE.md` §13）:
> 1. コントローラ先端のピボット校正（未補正だと数 cm の系統誤差が測定値に乗る）。
> 2. 試行ごとの Quest＋PC 同時リセット（`AlignmentManager.ResetForNewTrial` と UDP type=4 RESET の対）。無いと改悪防止ゲートと蓄積バッファが前試行を引きずり、試行が独立しない。**Real CP はここでは捨てない**（試行をまたいで使う値のため）。
> 3. 評価中のアンカー永続化の無効化（起動時復元があると「即ロック成功」と誤記録される）。
> 4. 自動アライン成立イベント `OnAutoAligned` の分離（`OnLocked` は手動 Lock でも鳴るため収束点として使えない）。
> 5. ワールド原点の移動検出（`TrackingOriginWatcher`）。Real CP も試行中のキーフレーム姿勢も、原点が動くと過去の座標系の値になる。残差やインライア率には現れないので、検出して破棄・無効化するしかない。

- **再投影誤差(px)**（目標: 数 px 以下）／**3D RMSE(cm)**（目標: 数 cm 以下）。
- **姿勢誤差**: 並進(cm)・回転(deg)・スケール誤差(%)。
- **オーバーレイ一致**: PSNR/SSIM（照明差の影響に注意、構造的指標併用）。
- **コールドスタート成功率・収束時間**、**経時ドリフト**、**追従のフレームレート/レイテンシ**、**サーマル下の持続性**。
- テストプロトコル: 接地真値（実測フィデューシャル、トラッキング済みコントローラで既知点接触）を定義し、複数シーン・**複数照明条件**で反復。

## 12. 設計判断（確定）と残課題

確定:
- 同一空間・相似変換(7自由度)・重力事前拘束。
- `.ply` 基本線＋強化モードの層構造。
- Environment Depth / MRUK を依存に含める（不可時は縮退）。
- 二層計算配置（追従=オンデバイス、大域=オンデバイス or UDP オフロード）。
- 特徴: オンデバイス XFeat(+LighterGlue)/ORB、PC SuperPoint+LightGlue（§5.3）。
- UDP プロトコル（§5.4）、追従レート/予算（§5.5）、見回し所作（§6.1）。

**前提の現状（v5 で更新）**:
- **R0（解決済み）**: aras-p レンダラの Quest 3 スタンドアロン動作 → **scalabroom 基盤＋OpenXR Multi-Pass＋Vulkan＋素の v1.1.1 で実機クリア**（両眼描画・貼り付き・ソート安定・72fps 圏内）。採用構成は CLAUDE.md §0/§2 に固定。
- **R1（今回は不採用に確定）**: Sentis でのオンデバイス特徴抽出・VPR は**今回採用しない**。重い CV は PC オフロードを一次経路にする（オンデバイスは将来オプション）。よって on-device 推論の実時間可否は当面ブロッカーから外す。
- **R2（確定）**: オフロード通信は**実装の簡素さを優先し UDP ベストエフォート**を採用（13B ヘッダ＋ JPEG チャンク、ビーコン自動検出）。取りこぼし時は再キャプチャで対応し、NACK 再送は必要が出たら追加（§5.4）。

残課題（実測ベースの調整）:
1. 各閾値（キーフレーム選択・パララックス・RTO・追従レート）の実機チューニング。
2. 量子化モデル（FP16/Uint8）の精度/速度トレードオフの実測と最終モデル確定。
3. オンデバイス大域ローカライズが実時間に乗るか否か（乗らなければ UDP 既定）。
4. サーマルスロットリング下での持続性能の検証。
5. 仮想レンダ DB のドメインギャップ（フローター・視点依存）が基本線の成功率に与える影響の実測（§5.1）。
6. PCA-RGB と Environment Depth の再投影整合誤差の実測（§8）。
7. オンデバイス・メモリ総量が予算に収まるか（§5.6）。

## 13. 用語

- **VPT**: ビデオパススルー。**3DGS**: 3D Gaussian Splatting。
- **PCA**: Passthrough Camera API（Quest 前面カメラへのアクセス）。実装は Meta XR SDK の **`PassthroughCameraAccess`** コンポーネント（MRUK v81+、Building Block「Passthrough Camera Access」）。画像・内部パラメータ K・ワールド姿勢・タイムスタンプ・左右カメラを提供。詳細は `ImplementationSpec.md` §1/§14。
- **Environment Depth**: Quest 3 のリアルタイム・メートル単位の環境深度（Depth API）。
- **MRUK**: Meta MR Utility Kit（シーン理解：平面・メッシュ・アンカー）。
- **相似変換 / Sim(3)**: スケール付き剛体変換（7自由度）。
- **PnP**: 2D-3D 対応からカメラ姿勢を解く。**ICP**: 点群の精密位置合わせ。
- **hloc**: 階層的ローカライズ（大域検索→局所マッチ→PnP）。
- **VPR**: Visual Place Recognition（場所認識・画像検索）。
- **XFeat / LightGlue / SuperPoint / ORB**: 局所特徴・マッチング手法。
- **DBoW / GeM / NetVLAD / SALAD**: 画像検索・大域記述子手法。
- **KLT**: 疎特徴の追跡。**one-euro filter**: 低遅延スムージング。
- **NACK**: 欠落分のみ再送を要求する否定確認応答。
- **UDP オフロード**: 重い計算を UDP で外部 GPU PC に委譲する構成。
