# VPTAligned3DGS

作成済みの **3D Gaussian Splatting（3DGS）シーン**を、Meta Quest 3 の**ビデオパススルー（VPT）**と**自動で位置合わせ**して重畳表示する XR アプリ。
位置合わせは「手動で粗合わせ → パススルーカメラ画像を COLMAP DB に再ローカライズして Sim(3) を自動推定」という二段構えで行う。

> このファイルは **使い方（運用手順）** の索引。設計の意図は [`Specification.md`](Specification.md)、実装契約（確定値・§13 パラメータ）は [`ImplementationSpec.md`](ImplementationSpec.md)、Unity/XR の運用規約と最優先の前提は リポジトリ直下の [`CLAUDE.md`](../CLAUDE.md) を見る。

---

## 1. 全体像

3 つのコンポーネントが連携する。

```
[Quest 3 アプリ]  --UDP-->  [PC: run.py (Windows)]  --共有フォルダ-->  [WSL2: localize.py (CV)]
  Unity/URP/OpenXR          受信・返送・GUI              hloc 再ローカライズ→Sim(3)
  3DGS 表示 + パススルー      (ポート 50000/50001/50002)   (SuperPoint/NetVLAD/LightGlue/PnP)
       ^                                                          |
       +-------------------- Sim(3) を返送(type=3) ----------------+
```

- **Quest**: 3DGS を両眼描画しパススルーに重畳。左グリップでパススルー画像＋カメラ内部/姿勢を UDP 送信。PC から届いた Sim(3) を（品質ゲート通過時のみ）splatRoot に適用。
- **PC(Windows) `run.py`**: UDP 受信・保存、LAN ビーコン、Sim(3) の Quest 返送、GUI。**重い CV は動かさない**。
- **WSL2(Ubuntu+CUDA) `localize.py`**: パススルー画像を COLMAP DB に再ローカライズし、複数キーフレームのカメラ中心から **Umeyama+RANSAC で Sim(3)** を解く。

> **なぜ WSL2 か**: pycolmap は Windows ネイティブでクラッシュするため、CV は WSL2 で動かす（詳細 `CLAUDE.md` §13）。

## 4. 初回セットアップ（一度だけ）

### 4-1. Unity プロジェクト
1. `unity/projects/VPTAligned3DGS` を Unity 6000.3.10f1 で開く（パッケージは manifest 記載のものが自動解決）。
2. Build Profiles で **Android / ARM64 / IL2CPP / Vulkan** に切替。OpenXR の Render Mode = **Multi-Pass**。
3. `GaussianSplatURPFeature` が **PC・Mobile 両方の URP Renderer** に付いていることを確認（片方だけだと実機で 3DGS が見えない）。

### 4-2. 3DGS アセットの作成（`.ply` → GaussianSplatAsset）
`.ply` は実行時に直接読まない。Editor で変換する:
- メニュー **Tools > Gaussian Splats > Create GaussianSplatAsset** → 入力 `.ply` を指定 → 生成されたアセットを `GaussianSplatRenderer` に割当。
- Quest 向けは品質 **Medium 以下**を起点に。GPU バッファ 128MB 制限に注意（採用シーンは約15万スプラット）。

### 4-3. WSL2 の CV 環境

source ~/vptcv/bin/activate
python -m pip install -U pip wheel

cd /mnt/c/Users/heatf/Desktop/VPTAligned3DGS/server
pip install -r requirements.txt -r requirements-cv.txt          # numpy/opencv/pycolmap

## 5. 毎回の実行手順

> **要点**: 「PC で `run.py` → WSL2 で `localize` → Quest で部屋を歩いて左グリップ送信」。`run.py` の 1 回の起動＝1 セッション。

**① Windows（受信・返送・GUI）**
```powershell
cd C:\Users\heatf\Desktop\VPTAligned3DGS\server
python run.py                      # 起動毎に received/session_<時刻>/ と cv.json を生成
```

**② WSL2（CV 監視。最新セッションを自動追従）**
```bash
source ~/vptcv/bin/activate
cd /mnt/c/Users/heatf/Desktop/VPTAligned3DGS/server
python -m vptserver.cv.localize    # 引数なし（cv.json / 自動検出でシーン解決）
```

**③ Quest（アプリ起動）**
1. アプリを起動しパススルー＋3DGS が出るのを確認。
2. 3DGS がズレていれば、まずコントローラで粗合わせ（→ §5-1）。
3. **部屋の 3 か所以上の別位置**から左グリップでキーフレーム送信 → 数枚たまると自動で Sim(3) が適用され、貼り付きが合っていく。

新しいセッションは **`run.py` を再起動するだけ**（新フォルダ＋cv.json 自動生成、手動クリア不要）。
実験で試行を繰り返すときは再起動不要で、Quest の HUD「▶ 試行 開始」が PC へ RESET を送って新セッションに切り替える（→ §9）。

**位置合わせの永続化（P4）**: Lock（または自動アライン確定）時に、実部屋へ空間アンカーを**2個**保存し、合わせ込み結果を `persistentDataPath/vptalign_<modelId>.json` に記録する。次回起動時に自動復元（片方のアンカーが再発見できなくても復元可）。`modelId` は `GaussianSplatController` の欄（空なら 3DGS アセット名を自動採用）。複数モデルを使う場合はモデルごとに別ファイルになるので干渉しない。やり直したいときは `AnchorPersistence.ClearSaved()`。

### 5-1. コントローラ操作（`AlignmentManager`）

| 入力 | 動作 |
|---|---|
| 右スティック | 頭の向き基準で水平移動（前後・左右）|
| 左スティック Y | 垂直移動（上下）|
| 左スティック X | ヨー回転（頭の位置を軸に）|
| 右トリガー / 左トリガー | 拡大 / 縮小（頭を Pivot に等方スケール）|
| A | 確定（Lock）→ アンカー保存 |
| B | 初期姿勢にリセット |
| X | 3DGS 表示 / 非表示トグル |
| Y | 再調整（Unlock）|
| 右スティック押込 | 目の前に呼び寄せ（Recenter）|
| 左スティック押込 | 水平化＋床スナップ（M2）|
| **左グリップ** | 短押し=単発送信 / 長押し1s=自動送信モードのトグル（自動位置合わせ）|
| **右グリップ** | **HUD の表示/非表示トグル**（ON 時に頭の前方へ再配置）|

> **起動直後スプラットは非表示**（`AlignmentManager.startHidden`、既定 on）。位置合わせ前の
> スプラットは実世界と無関係な場所に浮いていて視界を塞ぐだけで、しかも「もう合っている」と
> 誤解させるため。以後の表示は**いま何を見る作業か**で自動的に切り替わる（§5-3）。
> X でいつでも手動で切り替えられる。

**実験中（`ExperimentController.experimentInputEnabled` が ON のとき）は割当が変わる**。
両手が塞がる場面があるので、主要操作は HUD の Poke だけでなく物理ボタンからも打てる。
このとき**姿勢を変える手動操作（A/B/Y・スティック・トリガーのスケール）は封じられる**
— 実験中に B（初期姿勢リセット）を誤爆するとその試行の測定が無効になるため。X（表示トグル）だけは残る。
**例外は Real CP の測定中と Virtual CP の編集中で、スティック操作だけは通す**（下表の最終行 → §9-1 の 2b・3）。

> **用語: Virtual CP と Real CP**（HUD の表記。§9-1 も同じ呼び方）
> CP は control point の略で、`CP_01` … `CP_06` は**実在する 1 つの物理的特徴**（机の角など）を指す。
> その 1 点につき記録する座標が 2 つあり、混同しないよう呼び分ける。
>
> | 呼び方 | 何の座標か | どこで決めるか | ログ名 |
> |---|---|---|---|
> | **Virtual CP** | 3DGS モデル座標（splatRoot ローカル）| Unity Editor、または VR 内の `Edit Virtual CP`（§9-1 の 2b）| `cp_model_edit` |
> | **Real CP** | 同じ特徴の**実物**のワールド座標 | VR 内の `Set Real CP`（§9-1 の 3。コントローラ先端で実物に触る）| `cp_survey` |
>
> 誤差は `err = |T(Virtual CP) − Real CP|` で、**どちらも Sim(3) の推定には使わない**（→ §9-3）。
>
> **画面に出る名前は `VCP_01` / `RCP_01`**（V = モデル上の球、R = 実測した橙の点）。以前はどちらも
> `CP_01` で、**見分けが色だけに載っていた** —— 測定中は同じ点の 2 つの側がすぐ隣に並ぶうえ、
> 色の印象はパススルーの背景と照明で変わる。HUD の指示も同じ文字で書くので、
> `Walk to RCP_01` と出たらその文字をワールドの中で探せばよい。
> 呼び分けは **HUD・ワールドのラベル・本書の文言だけ**で、クラス名（`ControlPointMeasure` / `ControlPointEdit`）・
> UDP イベント名・`controlpoints_<modelId>.json` の鍵は `CP_01` のまま（過去ログと解析スクリプトの互換のため）。
> 写真測量の用語では、推定に使わず検証にだけ使うこの 6 点は control point ではなく
> **check point（検証点）**にあたる。呼称は CP のまま通し、論文でその旨を書く。

| 入力 | 動作 |
|---|---|
| **B（右）短押し** | 試行 開始 / 次の試行へ。**Virtual CP 編集中のみ**「この点をビルド値へ戻す」|
| **B（右）長押し 1s** | **Virtual CP 編集中のみ**: 動かした点を**すべて**ビルド値へ戻す |
| **A（右）短押し**（HUD 表記 `A tap`）| **仮置きを確定して次の点へ**（Real CP 測定中・Virtual CP 編集中。→ 下の「置く → 確かめる → 確定する」）。編集中で仮置きが無ければ「置かずに次の点へ」（＝ `Skip`）。どちらでもなければ **Real CP の測定開始**（→ §9-1。実験の前に 1 回だけ）|
| **A（右）長押し 1s**（HUD 表記 `A hold`）| **Virtual CP の VR 編集** 開始 / 終了（→ §9-1 の 2b。**位置合わせ前だけ**）|
| **Y（左）** | 試行中は**中断**、Real CP 測定中は**測定の中断**、Virtual CP 編集中は**編集の終了**、それ以外は**先端校正の開始/終了**（文脈で切り替わる）|
| **X（左）** | 3DGS の表示 / 非表示 |
| **右トリガー** | Real CP 測定中・Virtual CP 編集中: この位置へ**仮置き**する（まだ記録されない。何度でも置き直せる）|
| **左トリガー** | Real CP 測定中・Virtual CP 編集中: 仮置きがあれば**取り消し**、無ければ**1 つ前の点に戻る** |
| 左グリップ | 単発送信（短押し）/ 自動送信トグル（長押し）。**試行中は無効**|
| **スティック（両手）** | **Real CP 測定中・Virtual CP 編集中のみ**: 3DGS を動かす。§5-1 の割当そのまま（右=水平移動 / 左=上下・ヨー / 押込=呼び寄せ・水平化）。**トリガーのスケールは含まない** |

> **置く → 確かめる → 確定する（CP を設定する共通の流れ）。**
> Real CP の測定も Virtual CP の編集も、**右トリガーだけでは確定しない**。
>
> | 段階 | 操作 | 起きること |
> |---|---|---|
> | 1. 仮置き | **右トリガー** | Real CP は**白い点**（ラベル `RCP_01 ?`）、Virtual CP は**球が白**になってその位置へ移る。**まだ記録も進行もしない** |
> | 2. 確かめる | 頭を動かす／別の角度から見る | 奥行きは両眼視差と運動視差で分かる。ずれていたら**右トリガーで何度でも置き直す** |
> | 3. 確定 | **A 短押し** | ここで初めて記録され（`cp_survey` / `cp_model_edit`）、**次の点へ進む**（`VCP_01` → `VCP_02`）|
> | 取り消し | **左トリガー** | 仮置きを捨てて押す前の状態へ戻る（点は進めない）|
>
> HUD はタイトルが `Confirm RCP_01?` / `Confirm VCP_01?` に変わり、確定待ちだと分かる。
> 確定するまで `_edited` にも入らず、測量の無効化も起きない。
> **理由**: 1 回のトリガーで確定していた頃は、**押した瞬間の先端位置がそのまま最終値**だった。
> トリガーを引く動作自体でコントローラが数 mm 動くうえ、当てた場所が狙った特徴かを確かめる
> 機会が無く、ずれても「1 つ戻る」（＝前の点まで巻き戻す）しか手が無かった。
>
> **測定中の A は測定を中断しない。** 確定を A に載せた以上、余分な 1 押しで 6 点の測量が
> 消えるのは危険すぎる。中断は **Y** に一本化した（HUD の `Cancel` も `[Y]` と表示する）。

**HUD のボタンには対応する物理ボタンが `Calibrate tip [Y]` のように角括弧で添えて表示される**
（山吹色）。指示文の中に出てくるボタン名（`Press B, then walk …` の `B` など）も同じ色。
**HUD の全ボタンに物理割当がある**（Poke 専用のボタンは無い）。割当が文脈で変わるボタンは、
**その割当が効かない局面ではボタンごと淡色（無効）になる** — Real CP の測定中に `Calibrate tip` は
押せない（そのとき Y は測定の中断）。割当タグを出し分けるのではなく無効にするのは、
出し分けだけだと編集中に `Set Real CP` を Poke できてしまい、測定と編集が同時に走って
右トリガーが両方に効くため。

> **かつて `[poke]`（＝パネルを手で突く操作しかない）と表示していたボタンは廃止した。**
> 空中に浮いた 40px の板をコントローラで 3cm 以内まで突く操作は実機で狙えず、
> 「何を Poke するのか分からない」となった。編集中の `Skip` / `Revert this` / `Revert all` は
> A 短押し / B 短押し / B 長押しへ移した（編集中はどれも他の役を持たない）。Poke 自体は
> 残っているが、**物理ボタンだけで一通り操作できる**ことを不変条件として保つ。

> **A の短押しと長押しを分けた理由**: Virtual CP の編集は**実験の前に一度あるかどうか**の
> 操作なので、専用のボタンを 1 つ潰すほどではない。左グリップ（単発送信 / 自動送信）と同じ
> 短長押しの慣用に揃えた。長押しは**指を離す前に発火**し、触覚で「離してよい」を伝える
> ——1 秒を目で測れないため。

> **なぜこの 2 つの局面だけスティックを開けるのか**: 位置合わせ前の CP の球は実世界と無関係な場所
> ——壁の向こうや天井裏——に出るので、球を頼りにしたくても近づけない。シーンごと手元へ
> 寄せられれば「いま何番の点か」を球で確認できるし、Virtual CP の編集にいたっては
> **モデルに手が届かないと何もできない**。ここで動かした姿勢は**測る値に影響しない**
> （Real CP の測定が測るのは実物にコントローラ先端を当てたワールド座標だけ、編集が書くのは
> splatRoot ローカル座標だけで、どちらも splatRoot の姿勢に依らない）し、試行開始時に
> `ResetForNewTrial` が初期姿勢へ戻すので試行にも持ち込まれない。
> トリガーを除くのは、どちらの局面でも両トリガーが「記録／置き直し」「1 つ戻る」だからで、
> 開けると 1 点触るたびにスプラットが伸び縮みしてしまう。
>
> **ただし Real CP の測定中のスティックは「球を視界に入れる」ためだけ**で、球を実物に
> 重ねる作業ではない。重ねてしまうと先端が球に釣られて実物からずれ、それがそのまま
> グラウンドトゥルースの誤差になる。HUD もそう書いてある
> （`bring the markers into view` ／ `The yellow sphere only says which point — it is NOT on the real object`）。

> **Y が 4 役なのはなぜか**: 先端校正は試行中にも Real CP の測定中にも Virtual CP の編集中にも
> 行わないので、「試行中＝試行の中断」「測定中＝測定の中断」「編集中＝編集の終了」
> 「それ以外＝校正」で時間的に競合しない。HUD のラベルもその時の意味に変わる。

> **Real CP の測定に「スキップ」は無い。** 1 点でも欠けると誤差の計算に使えないので、
> 飛ばせても意味がない。代わりに左トリガーで 1 つ前に戻って測り直す。

> **左グリップは試行中に無効化される**: 誤って押すと自動送信が止まったり余計なキーフレームが
> 混ざって、その試行が壊れるため。HUD の送信系ボタンも試行中は淡色になり反応しない。

手動で粗合わせしたくなったら `ExperimentController.experimentInputEnabled` を OFF にすると
§5-1 の通常割当に戻る。**HUD にこれを切り替えるボタンは無い**（実験中に触れるところに置くと、
誤爆一発で試行の測定が無効になるため。Inspector から明示的に切る）。

> **入力の左右指定**: グリップ・スティック・トリガーは利き手設定で左右が入れ替わる `Primary/Secondary` ではなく、**明示的な `RawAxis*/RawButton` の L/R** を使う（実装＝この表で確定）。A/B/X/Y は左右固定で曖昧さなし。

### 5-1b. アバターの表示/非表示（`AvatarVisibility`）

シーンの `Avatar` に付いている `AvatarVisibility` の **Show Avatar** チェックで切り替える。
Editor では操作した瞬間に反映され（Play 中・Edit 中どちらでも）、状態はシーンに保存される。
実行時は `SetVisible(bool)` / `Toggle()` から。

| Hide Mode | 挙動 | 使いどころ |
|---|---|---|
| `RenderersOnly`（既定）| Renderer だけ切る。IK は回り続ける | 再表示が即座で姿勢も崩れない。通常はこちら |
| `DeactivateObject` | GameObject ごと切る。IK/Animator も止まる | 負荷を下げたいとき。再表示直後の 1 フレームは姿勢が落ち着かないことがある |

> **Real CP の測定中は消しておくのが無難。** 実物の点をコントローラ先端で触るとき、仮想の腕が
> 実際の腕に重なって描画されると接触点が隠れて狙いが甘くなる。測定値に直接効く。

### 5-2. HUD（`AlignmentHud`）

右グリップで表示/非表示。製品ビルドでは `hudEnabled=false` で丸ごと無効化。
`Assets/Scripts/Experiment/` のコンポーネントがシーンにあると**実験者向けの表示**になり、無ければ位置合わせ用の簡易表示になる。

- **局面で表示が変わる**。上から「今なにをすべきか」（大きな指示文＋色帯）→ プログレスバー → ライブ数値 → 準備チェック → ボタン → 診断（小さく常時表示）。
- **頭に緩く追従**。視線から 24° 以上外れたときだけ滑らかに追いつく。正面ではなく少し下に置くのでパススルーを塞がない。**手を近づけている間は動かない**（Poke するボタンが逃げないように）。
- **表示更新は 10Hz**。毎フレーム文字列を作ると GC で 72fps を削るため。
- **文字列はすべて英語**。実機で読むのは HUD だけなので混在させない（日本語はログとインスペクタのツールチップに限る）。
- **文字が枠の外へ出ない**。全テキストが折り返し＋ best fit（下限は指定サイズの 60〜70%、最小 10px）で、長い行は枠外へ伸びずに縮む。特に**準備チェックの行は 2 行ぶんの高さ**を取ってある（警告が全部出ると 1 行では幅の 1.4 倍になるが、ここは一番読ませたい行なので縮めずに折り返す）。行を増やすときはパネル高 `h`（実験用 688px）も合わせて見直すこと。

| 色 | 局面 |
|---|---|
| 琥珀 | 準備不足（不足している項目が指示文に出る）|
| 青 | 試行を開始できる |
| 青緑 | 収集中（歩き回る。残り秒数がバーに出る）|
| 紫 | **Real CP の測定中**（`SET REAL CONTROL POINTS`。次に触る CP 名と進捗 n/6）|
| 桃 | **Virtual CP の編集中**（`EDIT VIRTUAL CONTROL POINTS`。触るのは実物ではなく**スプラット**）|
| 緑 | 収集完了 / 全試行完了 |
| 赤 | 試行を破棄（トラッキング原点が動いた → §7-5）|

ボタンは Poke（コントローラ先端で触れる）でも押せるが、**角括弧の物理ボタンで押すほうが確実**。
押せない状況のボタンは淡色になり、Poke にも物理ボタンにも反応しない。

**置いてあるのは実験の流れに要るものだけ**:

| ボタン（画面の表示どおり） | 用途 |
|---|---|
| `Start trial [B]` / `Abort [Y]` | 試行の開始と中断。準備（Real CP を含む）が揃うまで押せない |
| `Calibrate tip [Y]` / `Finish calib [Y]` | 先端のピボット校正。毎セッション必須。**Real CP 測定中・編集中・試行中は淡色**（そのとき Y は別の役）|
| `Set Real CP` / `Redo Real CP` `[A tap]` / `Cancel [Y]` | 実物側の位置を実測する。**実験の前に 1 回だけ**（→ §9-1）。**測定中の割当タグは `[Y]`**（A は「仮置きの確定」に取られる）。**編集中は淡色** |
| `Edit Virtual CP [A hold]` / `Done editing [Y / A hold]` | モデル側の CP を VR 内で置き直す。**位置合わせ前だけ**押せる（→ §9-1 の 2b）|
| `Confirm [A]` / `Skip [A]` | 仮置きがあれば**確定して次の点へ**（測定中・編集中とも）。仮置きが無いときの `Skip`（置かずに次へ）は**編集中のみ**で、**最後の点では淡色**（次が無い。終わるのは `[Y]`）|
| `Revert this [B]` / `Revert all (n) [B hold]` | 編集中のみ: 現在の点をビルド値へ戻す ／ 動かした点を全部戻す。動かしていなければ淡色 |
| `Show splats [X]` / `Hide splats [X]` | 3DGS とパススルーを見比べる。ラベルは今の状態に応じて変わる |

> **やり直しを `Re-set` とは書きません。** このプロジェクトで RESET と言えば試行リセット
> （UDP type=4）を指すので、押すと試行が飛ぶと読まれます。`Redo Real CP` にしてあります。

準備チェックの CP は **2 段**で、Virtual CP（Editor で配置）と Real CP（実測）の両方が揃って
初めて緑になります（`No Virtual CP` → `Real CP not set` → `Real CP 6`）。片方だけで緑にすると、
実測を忘れたまま試行を始めてしまうためです。VR 内で Virtual CP を動かした場合は
`▲ Virtual CP edited 2` が並んで出ます（Editor のシーンと実機の値が
食い違っている状態なので、後で取り込みが要ることを忘れないため → §9-1 の 2b）。

> **`Edit Virtual CP` が淡色で押せないとき**は理由が HUD に出ます。多いのは
> 「**位置合わせ済み**（`Pose is already aligned …`）」——これは仕様です（§9-1 の 2b）。
> ほかに「先端が未校正」「Real CP の測定中」「試行中」。姿勢を B でリセットすれば押せるようになります。

> 手動送信（`Auto` / `Send one`）と手動位置合わせ（`Manual` / `Unlock` / `Recenter`）は**外した**。
> 送信は試行が自動で制御するので前者は押せば進行中の試行を壊すだけ、後者は自動位置合わせを
> 評価する実験では使う場面が無く、誤爆すると測定が無効になるため。
> （実験コンポーネントが無いシーンの簡易 HUD にはこれらが残っている:
> `Splats [X]` / `Auto [L grip hold]` / `Send one [L grip tap]` / `Unlock [Y]` /
> `Recenter [R stick]` / `Level + floor [L stick]` の 2 列 3 行。この局面では姿勢操作が
> 全部生きているので、割当は文脈で変わらない。）

準備チェックは 3 状態:

| 表示 | 意味 |
|---|---|
| `✓`（緑）| このセッションで確認済み |
| `▲`（琥珀）| 値はあるが**このセッションでは未検証**（例: `▲ 先端 前回値`）。試行は開始できない |
| `✗`（赤）| 未設定・未応答 |

> `▲` を作った理由: 「一度確認した」と「今この瞬間に有効」は別物で、前者を `✓` にすると
> false confidence になる。サーバの疎通表示と同じ考え方。

> **Real CP の測定中に「動いていない」と弾かれたら、その場で直すこと。** 前の点から先端がほとんど
> 動いていない記録は受け付けません（触覚で 2 回短く返り、理由が HUD に出ます）。
> 一度これを見逃して、1 か所に立ったまま右トリガーを 6 回引き、6 点すべてを同じ場所で
> 記録した試行が出ました。誤差は数メートルになりますが、位置合わせが悪いのか測り方が
> 悪いのかは数字からは区別がつきません。

### 5-3. スプラットの表示は「いま何を見る作業か」で決まる

3DGS の表示は局面に応じて**自動で切り替わります**。基準は 1 つだけ:
**モデルを見る作業なら出す／実環境を見る作業なら消す**。

| 局面 | スプラット | 理由 |
|---|---|---|
| 起動直後 | **非表示** | 位置合わせ前のスプラットは実世界と無関係な場所に浮いて視界を塞ぐうえ、「もう合っている」と誤解させる |
| `Edit Virtual CP` 開始 | **表示** | 触る対象がスプラットそのもの。見えないと何もできない |
| `Set Real CP` 開始 | **非表示** | 見るべきは実環境だけ。位置合わせ前のスプラットは、先端を当てたい実物そのものを覆い隠す（見た目ではなく**測定精度**の問題）|
| 試行の収集開始 | **非表示** | 同上。初期姿勢へ戻された直後のスプラットは邪魔にしかならない |
| 姿勢が適用された時点 | **表示** | ここで初めて見る意味が出る |
| X | 手動トグル | いつでも上書きできる |

> **姿勢適用は「収集が終わった時点」ではありません。** CV の結果は収集終了より遅れて
> 届くことがあり、その間に出しても初期姿勢のスプラットが見えるだけだからです。
> 自動で出すのは 1 試行につき 1 回だけなので、そのあと X で消して見比べるのは妨げません。

> **CP の球・ラベル・橙の点は、Real CP の測定中と Virtual CP の編集中はスプラットに連動しません**
> （`ControlPointMeasure.GizmosActive`）。測定中はスプラットを消しますが、球まで一緒に消えると
> 「次はどの点か」の案内が丸ごと無くなるためです。この 2 局面での X は「スプラットを覗く／隠す」
> だけの意味になります。位置合わせ済みの通常表示では従来どおり 3DGS と一緒に消えます。
> なお**入力の受付はどちらの局面でも表示に連動しません**（X で消したときに、押しても記録されない
> 状態へ黙って落ちるのを防ぐため）。

## 6. ネットワーク（重要）

PC と Quest は**同一 LAN でユニキャストが通る**必要がある。

- **自宅ルータ等**: `run.py` の LAN ビーコン（UDP 50001）を Quest が自動検出 → 設定不要。
- **大学 / 公共 WiFi**: ブロードキャストが遮断されビーコンが届かないことが多い。切り分けと対処:
  1. PC から `ping <QuestのIP>` を実行。
  2. **返る**（ユニキャストは通る）→ Unity の `UDPManager` インスペクタ **Manual IP Address** に PC の IPv4（`ipconfig` で確認）を入れて再ビルド。ビーコン無しで往復成立。
  3. **返らない**（クライアント分離）→ 同一 WiFi では直接通信不可。PC のモバイルホットスポット / スマホテザリング / トラベルルータで**私設 LAN** を作る（運用中インターネット不要）。

ポート: **50000**=データ(Quest→PC) / **50001**=ビーコン(PC→LAN) / **50002**=結果 Sim(3)・PONG(PC→Quest)。

### 6-1. 疎通の確認（HUD のチェック表示）

Quest は 2 秒ごとに PING を送り、PC が PONG を返す。**HUD の `● Server` はこの往復が成立している証拠**で、
RTT[ms] も出る。**送信先 IP を知っているだけでは ● にならない**（IP は前回起動時の学習値が残るので、
`run.py` を止めていても埋まってしまう。往復を見ないと疎通判定にならない）。

PONG には WSL2 の CV ワーカの生存も載る。HUD の `● CV` がこれ。
**`run.py` だけ動いていて `localize` を起動し忘れる**と、キーフレームは PC に届いて保存されるのに
Sim(3) が永遠に返らず、試行は必ずタイムアウトする。外からは「位置合わせが失敗した」ようにしか
見えないので、この表示で始める前に気づけるようにしてある。両方 ● になるまで試行は開始できない。

準備チェックの行（HUD 中段）は `●`=OK / `▲`=未検証 / `✕`=未達。

| HUD の表示 | 意味 | 対処 |
|---|---|---|
| `✕ Server` ＋ 診断行 `… (auto) — no reply` | PING に PONG が返らない | `run.py` を起動。それでも駄目なら §6 のネットワーク切り分け |
| `✕ CV` | `run.py` は応答するが CV ワーカ未検出 | WSL2 で `python -m vptserver.cv.localize` を起動 |
| `▲ CV 3` | CV が 3 枚処理中（数秒かかる） | 待つ。停止ではない |
| `● Server 3ms   ● CV` | 疎通 OK | 試行を開始できる |

診断行（HUD 下部）には PC 側のセッション名と受信枚数も出る。**「Quest の送信数」と「PC 受信枚数」を
見比べると、届いていないのか、届いたが解けていないのかを切り分けられる。**
書式は `<IP>:<port> (auto|manual) <RTT> · cv … · auto on|off · <状態> · input …`。
`auto`=ビーコンで自動検出した送信先 / `manual`=`UDPManager.manualIPAddress` で固定した送信先。
**HUD の文字列はすべて英語**（`UDPManager.TargetDescription` を含む）。ログとインスペクタの
ツールチップだけが日本語で、こちらは HUD に出ない。

## 7. 品質ゲートと確定条件（自動位置合わせの堅牢化）

### 7-0. 残差だけでは正しさを判定できない（設計の前提）

**Sim(3) の残差が小さいことは、解が正しいことを意味しない。** 実機で「採用 1 件で確定したが位置が
まるで違う」が起きたのはこれが原因だった。2 種類の退化があり、どちらも残差では検出できない。

| 退化 | 何が起きるか | 対策 |
|---|---|---|
| **共面配置＋反射の自由推定** | 3 点は必ず同一平面上。反射を許すと「その平面に関する鏡映を掛けた解」が**完全に同じ残差**を与えるため、2 解を区別できずコインフリップになる。**頭の高さを変えずに部屋を歩くとカメラ中心はほぼ共面**なので、枚数を増やしても起きる | **反射を負に固定**（下記） |
| **共線配置** | 一直線に歩くと、その直線まわりの回転が拘束されない。反射を固定しても直らない | **配置ゲート**（下記） |

数値検証: 共面 6 点で自由推定は 47%、3 点では 68% が誤り。反射を固定すると 0%。
共線配置は反射を固定しても 100% 誤るが、配置ゲートが棄却する（`tests/test_alignment_gates.py`）。

### 7-1. 反射（負スケール）の固定

COLMAP は右手系、Unity は左手系で、aras-p は PLY の座標を軸反転せず読む。つまり**手性の違いは
座標規約から決まる定数**であって、推定すべき未知数ではない（§6 / `Specification.md` §8）。
`geometry.umeyama(handedness=-1)` で det(Q)=-1 を強制し、常に負スケールの解にする。

自由推定へ戻したい場合は `cv.json` の `handedness` を `0` にする（通常は不要）。

### 7-2. 品質ゲート（PC 側 / `vptserver/cv/gates.py`）

| 項目 | 既定 | 意味 |
|---|---|---|
| `min_inliers` | 30 | PnP インライアが少ないキーフレームは蓄積しない |
| `min_inlier_ratio` | 0.5 | 解のインライア率 |
| `max_rmse` | 0.05 m | world 残差 RMSE |
| `min_baseline_m` | 1.50 m | カメラ中心の最大間隔（**その場で首を振っただけを弾く**）|
| `min_second_extent_m` | 0.40 m | 第 2 主成分方向の広がり（**一直線に歩いただけを弾く**）|
| `expected_scale` | 未設定 | シーン既知スケール。**通常は使わない**（下記）|

### 7-2b. 精度は「どれだけ部屋を歩いたか」でほぼ決まる

実機の雑音（残差 RMSE 1.4〜3.5cm）に合わせて運用を模擬し、歩き方ごとにロック率と
確定後の誤差（部屋の隅での位置ずれ）を測った結果:

| 歩き方 | ロック率 | 誤差 中央値 | 誤差 90% | 使用 KF |
|---|---|---|---|---|
| その場で首を振る（0.5m）| 0% | — | — | — |
| 短く直線に歩く（3m）| 0% | — | — | — |
| 短くゆるい弧（3m）| 0% | — | — | — |
| **部屋を横切る（6m・弧）** | 92% | 15.6 cm | 31.9 cm | 20 |
| **部屋を回る（9m・大きな弧）** | **100%** | **9.9 cm** | 25.5 cm | 17 |

**ゲートにできるのは「足りていないときに確定させない」ことだけで、締めても精度は上がりません。**
実際、以前の設定（1.0m / 0.8m）では 9m 大きく回る歩き方しか通らず、**60 秒以内にロックしなく
なりました**。逆に緩めると直線歩行が通ってしまい 57% が誤ります。上の値はその中間で、
「不十分な歩行は確定させず、十分な歩行は確実に確定する」点に置いています。

> **実験者への指示が精度を決めます。** 「その場で見回す」「まっすぐ数歩」では確定しません。
> **部屋の中を大きく回るように歩いてください**（9m 程度）。それがそのまま精度に効きます。

#### `expected_scale` について（通常は使わない）

COLMAP の任意単位と実メートルの比は、その再構成に固有の固定値です（このシーンでは 0.96）。
`--expected-scale 0.96` で指定すると、そこから外れた解を棄却できます。

**ただし評価実験では使わないでください。** 上の実験のとおり、反射固定＋配置ゲート＋連続一致で
誤り率は既に 0% で、スケールゲートを足しても改善しません（不要）。一方でシーン固有の既知値を
推定に注入すると、論文の「メトリックスケールを解決する」という主張が弱くなります。
**推定した値が独立に実測した値とどれだけ一致したか**を結果として報告するほうが強い。

デバッグ時に「なぜ合わないのか」を切り分けたいときだけ使ってください（棄却理由がログに出ます）。

### 7-3. 確定条件（Quest 側 / `AlignmentManager`）

受信した Sim(3) を同種ゲート＋**改悪防止**（前回採用より明確に悪化した解は棄却）で判定したうえで、
**連続して一致する解が `minConsecutiveAgreements` 回（既定 2）揃って初めて「確定」**とする。

- 一致の判定は、2 つの解でスプラットの境界ボックス 8 隅が動く距離（既定 **15cm** 以内）。
  位置・回転・スケールに別々の閾値を置くより「見た目がどれだけ違うか」に直結する。
  境界ボックスの隅は原点から 6m 以上離れるため、ここを小さくしすぎると実機の雑音下では
  ほぼ成立しない（8cm にしたところ 60 秒以内にロックしなくなった）。
- 未確定の間も姿勢は適用する（収束の様子が見える）が、`Locked` にはせず永続化もしない。
- 収束時刻として記録するのは**確定した瞬間**（`OnAutoAligned`）。HUD には `一致 1/2 ずれ3cm` と進捗が出る。
- `minConsecutiveAgreements = 1` にすると従来どおり 1 件目で確定する。

> なぜ連続一致か: 悪条件の解はキーフレームが増えると跳ねる。独立に解かれた 2 つが同じ答えに
> 落ち着くことは、残差が小さいことよりずっと強い証拠になる。想定していない失敗にも効く。

### 7-4. 最小キーフレーム数

`cv.json` の `min` は既定 **5**。`solve_sim3_ransac` は **n < 5 では RANSAC を回さない**
（3 点抽出に意味がないため全点で 1 回当てはめる）ので、4 以下にすると外れ値除去が一切効かない。

棄却は WSL2/実機ログに理由付きで出る（`KF棄却:`, `Sim(3) 非公開:`, `Sim(3) 棄却:`）。

### 7-5. 前提: Quest のワールド原点が動かないこと（**残差では絶対に検出できない**）

Sim(3) は「COLMAP のカメラ中心」と「Quest ワールドのカメラ中心」の対応から解く。
このワールドが固定である、というのが暗黙の前提になっている。ところが Quest の原点は

- Meta ボタン長押し（再センタリング）
- ヘッドセットを外して被り直す／スリープからの復帰
- トラッキングロスからの復帰・空間の再ローカライズ

で **鉛直軸まわりの回転＋水平移動** の形で飛ぶ。飛んでも rmse もインライア率も悪化しない。
実機で「3 試行とも同じように位置合わせが間違う」という症状が出たとき、原因はこれだった。

実測（`analysis/check_tracking.py` の出力）:

```
215016 -> 215246  回転  37.7°  軸の鉛直成分 1.000  スケール 1.0011  水平移動 0.57 m  鉛直 -0.00 m
215016 -> 215449  回転  78.1°  軸の鉛直成分 1.000  スケール 0.9968  水平移動 0.52 m  鉛直 +0.00 m
```

**推定誤差ならこの形にはならない。** 誤差はいちばん弱く拘束される方向（傾き）に出る。
カメラ中心はほぼ同じ高さに並ぶので、ヨーと水平位置は逆に最もよく決まるパラメータになる。
その最もよく決まるはずの量だけが試行ごとに数十度ずれ、傾きは 0 — つまり座標系そのものが回っていた。

対処は 3 層:

| 層 | 実装 | 何を捕まえるか |
|---|---|---|
| Quest | `TrackingOriginWatcher` | `OVRPlugin` の recenter カウント / `OVRManager.TrackingLost` / 頭部姿勢の不連続（**速度**で判定。フレーム落ちで誤検出しないため）|
| Quest | `ExperimentController` が試行を**自動破棄** | 収集中に原点が動いたら試行番号を消費せず捨てる。HUD に赤で `Trial discarded` |
| Quest | `ControlPointMeasure` が Real CP を**無効化** | いつ動いても実測値は無効になる（Real CP はワールド座標なので、動く前の座標系の値になる）。HUD が測り直しを要求する |
| PC | `localize` の終盤残差警告 / `analysis/check_tracking.py` | じわじわ動く再ローカライズ（実機では末尾 4 枚が 0.4→0.8→1.9→2.8 m と伸びた）|

> 破棄した試行にも固有のラベル（`trial-NN`）を与えている。ラベルを使い回すと
> PC の `session_*/trial.json` と 1 対 1 に対応せず、あとから破棄分だけを除外できない。

**実験中の運用**: ヘッドセットを外さない。同じガードリアン空間のまま回す。Meta ボタンを長押ししない。
PC の画面を見たいときは外さずに一旦置く（外すとスリープ→再ローカライズで原点が動く）。

## 8. トラブルシューティング

### 8-0. CP のマーカーが実機でピンクになる／見つからない（＋Real CP の測定が CP_01 から進まない）

**ピンクの球＝マテリアルのシェーダが `null`（Unity のエラーシェーダ）。** プレイヤービルドは
「どのシーン／アセットからも参照されていないシェーダ」を削除します（stripping）。CP の球は
`new Material(Shader.Find("Unlit/Color"))` とコードだけで作るため、ビルド時の参照解析からは
見えず剥がされ、**Editor では正しく色が付くのに実機だけ `Shader.Find` が null を返します**。

対処は `Project Settings > Graphics > Always Included Shaders` に **`Unlit/Color`** を登録すること
（**登録済み**）。実機でラベルは読めるのに球だけピンク、という切り分けになるのは、uGUI が使う
`UI/Default` は既定でこのリストに入っていて `Unlit/Color` だけ漏れていたためです。
再発した場合は Logcat に `[CpGizmos] マーカーの球に使えるシェーダが 1 つも無い` が出ます
（黙ってピンクを出さないようにしてあります）。**コードで作るマテリアルのシェーダを増やすときは、
必ずこのリストにも足してください。**

球が「見つからない」だけならサイズの問題です → §9-1 の距離補正の注記を参照。

> **同じ原因で「Real CP の測定が終わらない」「編集が次の点へ進まない」が起きました（対策済み）。**
> `new Material(null)` は黙ってピンクを作るのではなく **`ArgumentNullException` を投げます**。
> その呼び出しが「次の点へ進む」処理より前にあったため、記録のたびに `Update()` ごと抜け、
> **測定は CP_01 から永久に進みませんでした**（7 回記録して 7 回とも `CP_01`、`cp_survey_done` が
> 出ず、HUD の準備チェックは `Real CP not set` のまま緑になりませんでした）。編集モードが
> 「CP_01 の次へ行けない」と見えたのも同じ例外です。**見た目の不具合が測定機能を止めていた**
> わけで、症状からは原因がまったく想像できません。
>
> シェーダ登録に加えて、`CpGizmos.Draw()` を通して**描画を状態遷移から切り離しました**。
> 以後、描画が落ちても球や点が出ないだけで測定・編集は最後まで進み、Console/Logcat に
> `[CpGizmos] ギズモの描画に失敗した` が 1 回だけ出ます。**ギズモを触るコードを足すときは、
> 状態を進める処理より後ろに置き、`CpGizmos.Draw()` で包んでください。**

### 8-1. 60 秒以内にロックしないとき

**HUD の実行中表示に、詰まっている段階がそのまま出ます。** 原因は 3 つのどれかです。

| HUD の表示 | 詰まっている段階 | 対処 |
|---|---|---|
| `送信 12  PC採用 0` | キーフレームが PC に届いていない、または再ローカライズに失敗している | ネットワーク（§6）、シーン DB の指定（`cv.json` の `scene`）、`min_inliers` を確認 |
| `PC で棄却: <理由>`（琥珀） | PC は解いているが公開ゲートで落としている | 理由がそのまま出る（rmse 超過 / インライア率 / 配置）。§7-2 の閾値を見直す |
| `採用 3  棄却 0  一致 1/2 ずれ25cm` | 解は届いているが、独立な解が一致しない | 歩き方が足りない。部屋を大きく回る（§7-2b）|

WSL2 のターミナルにも同じ理由が数値付きで出ます:

```
Sim(3) 非公開（ゲート不合格）: rmse=0.0912m(>0.08m) [n=24 inliers=18 rmse=0.0912 scale=-0.958 間隔=2.82 広がり=0.95]
```

> **ゲートの役割分担**: PC 側は「明らかにおかしい解」を落とすだけで、正しさの判定は
> Quest 側の連続一致が担います。PC 側を厳しくすると候補が一つも届かず、
> 一致判定まで到達せずロックしなくなります（実際にそうなりました）。

## 9. 評価実験の回し方

論文の実験をそのまま実施するための手順。関係するスクリプトは `Assets/Scripts/Experiment/`。

**評価は「収集時間 vs 精度」の 1 本の曲線に統一してあります**（→ §9-3）。かつて E1（オーバーレイ精度）
と E2（コールドスタート収束）を別々のモードで回していましたが、**1 回の歩行データから曲線全体を
オフラインで再構成できる**ので、実機でやることは「一定時間歩き回る」だけになりました。

準備は **2 段**です。どちらも**実験の前に 1 回**で、全試行で使い回します。

| 準備 | 頻度 | 何を決めるか |
|---|---|---|
| **コントローラ先端の校正**（→ 9-1 の 2）| セッションごとに 1 回 | 追跡原点から物理的先端までのオフセット |
| **Real CP の測定**（→ 9-1 の 3）| セッションごとに 1 回 | 各 CP に対応する**実物**のワールド座標 |

> **なぜ試行ごとに測らないのか**: 誤差 `|T(Virtual CP) − Real CP|` の両辺は、どちらも試行では
> 変わりません。Virtual CP は Editor で固定、Real CP は部屋が動かない限り固定です。
> 試行ごとに測り直しても、手間と測り間違いの機会が試行数ぶん増えるだけでした
> （実際、1 か所に立ったまま右トリガーを 6 回引いて 6 点すべてを同じ場所で記録した試行が出ました）。

> **唯一の前提は「Quest のワールド原点が動かないこと」**。Real CP はワールド座標なので、
> 再センタリングやヘッドセットの着脱で原点が回ると過去の座標系の値になります。
> `TrackingOriginWatcher` が検出すると Real CP は**自動的に無効化**され、HUD が測り直しを要求します
> （黙って古い値を使わせない）。→ §7-5

### 9-0. 実験の前提（ここを飛ばすと測定が無効になる）

| 前提 | なぜ必要か | 確認方法 |
|---|---|---|
| **サーバと CV の両方が応答** | `run.py` だけ起動して WSL2 の `localize` を忘れると、キーフレームは届くのに Sim(3) が返らず全試行がタイムアウトする | HUD の `● Server 3ms  ● CV`（→ §6-1）|
| **コントローラ先端の校正（毎セッション）** | Unity が返すのは本体内部の追跡原点で、実際に物へ当てる先端ではない。差は数 cm あり、測りたい量と同じオーダー。未校正だと系統誤差が丸ごと乗る。**前回の保存値は今の物理構成に対応している保証がない**ので、毎回やり直す | HUD が `✓ 先端 2.1mm`（緑）。`▲ 先端 前回値`（琥珀）は未検証状態で、このままでは Real CP を測れない |
| **Virtual CP が実物の特徴点に合っている** | ダミー座標のままだと何も測っていない | Editor の Control Points ウィンドウが仮座標を検出すると赤い警告を出す |
| **Real CP を測定済み（毎セッション）** | これが無いと、集めたデータから誤差を計算できない | HUD の準備チェックが `Real CP 6`（緑）。`Real CP not set` なら A で測る |
| **アンカー永続化が OFF** | 前回の姿勢が起動時に復元されると、「起動直後にロック成功」と誤記録される | `ExperimentController.forceExperimentMode=true`（既定）で自動的に OFF になる |

### 9-1. 準備

1. **Virtual CP の配置（シーンごとに一度・Editor）**: Unity で `Tools > VPTAligned3DGS > Control Points` を開き、`splatRoot` 配下に CP_01..06 を作る。
   Scene ビューでスプラットを見ながら、**実物側でも一意に指させる特徴**（机の角・棚の縁など）に合わせ、部屋全体に散らす。測定順は名前順。
   **ビルドするシーンが Virtual CP の正**で、実機が勝手にこのファイルを書き換えることはない。
   ただしマウス配置は奥行きが甘くなるので、実機で置き直して戻す道がある（→ 2b）。
2. **先端校正（セッションごとに毎回）**

   物理的にやることは「**すりこぎを回す**」動きです。

   1. **動かない 1 点を選ぶ** — 机の角、ネジの頭、棚の縁の角など。毎回同じ場所に先端を当てられるものが良い。
   2. その点に**コントローラの物理的な先端を押し当てる**。
   3. HUD の「先端校正」を押す。
   4. **先端をその点から離さないまま、本体だけを大きく振る。**
      前後左右に倒す、グリップを回す、当てる角度を変える。先端は動かず、本体の向きだけが変わる状態を保つ。
      コンパスの針を紙に刺したまま回すのと同じ。10 秒ほど続ける。
   5. 条件が揃うと自動で解けて保存される（「校正 終了」で早めに確定も可）。

   HUD は進行に応じて指示を変える。`サンプル 18/24 ・ 振り幅 32°/45°` と進捗が出て、
   **暫定残差**も表示される。残差が 8mm を超えると「先端がずれています」と出るので、当て直す。

   | やってはいけないこと | 何が起きるか |
   |---|---|
   | 先端が浮く・接点がずれる | 「先端が動かない」前提が崩れる。暫定残差が跳ね上がるのですぐ分かる |
   | 振りが小さい（数度だけ） | 式が似たものばかりで悪条件。**残差は小さく見えるのに解は数 mm ずれる** |
   | 向きを変えず平行移動するだけ | 回転が無いと情報が増えず、いつまでも条件を満たさない |

   > 2 つ目が厄介で、残差では検出できません。だから残差ではなく**振り幅（向きの広がり）**でゲートしています。
   > 「本体を大きく振ってください」と出ている間は条件未達です。

   校正が終わると**前回値との差**が出る。これがタダの整合性チェックになり、5mm を超えると警告する
   （コントローラや治具の取り違えはここに現れる）。差は `drift_mm` としてログにも残る。

   **なぜ毎回やるか**: オフセット自体はコントローラの物理的な性質なので原理的には変わらない。
   しかし「別のコントローラを握っている」「治具を付け外しした」「前回の校正がゲートぎりぎりで通っていた」
   はアプリからは判別できない。ずれていても全測定に系統誤差として乗り、**事後のログからは検出できない**。
   毎回校正すれば、推定値のセッション間のばらつき自体が誤差予算の情報になる。

   > 時間が無いときの逃げ道として、`ControllerTipCalibration.requireCalibrationEachSession` を OFF にすると
   > 前回値をそのまま使える。その測定は `tip_source="Restored"` として記録され、集計スクリプトが件数を警告する。

**2b. Virtual CP の VR 微修正（任意・先端校正のあと、Real CP の測定の前）**

Editor でのマウス配置は**視線方向の奥行きに歯止めが無い**ので、机の角に合わせたつもりでも数 cm
奥や手前に置かれていることがある。この誤差は `|T(Virtual CP) − Real CP|` の Virtual CP 側に乗るので、
**位置合わせの性能とは無関係に報告値を悪化させる系統誤差**になる。実寸で立って両眼視差と運動視差を
使い、**コントローラ先端を実際にその位置へ持っていく**ほうが正確に置ける。必要な点だけ直せばよい。

1. **A 長押し 1 秒**（または HUD の `Edit Virtual CP`）で開始。HUD が**桃**の
   `EDIT VIRTUAL CONTROL POINTS` になり、**スプラットが自動で表示される**（触る対象がスプラット
   そのものなので → §5-3）。
2. **スティックで 3DGS を手の届く位置へ寄せる**（Real CP の測定と同じ割当）。モデルに手が届かないと
   何も置けないので、これが前提。**寄せ方は測る値に影響しない**（記録するのは splatRoot
   ローカル座標なので、splatRoot をどこへ動かしても同じ値になる）。
3. 指示された CP（`Place VCP_04 on the splats`）に対応する**スプラット上の特徴**へ先端を当てて
   **右トリガー**＝**仮置き**（球が**白**になってその位置へ移る。まだ確定していない）。
   **頭を動かして別の角度から**、球が本当にその特徴に載っているか確かめる——奥行きは
   両眼視差と運動視差でしか分からないので、この確認が置き直しの本体。ずれていたら
   **右トリガーで何度でも置き直す**。**左トリガー**で仮置きを取り消せる。
   納得したら **A 短押し**（`Confirm`）で**確定**し、**自動で次の点へ進む**
   （VCP_01 → VCP_02 → … → VCP_06）。
   進んだかどうかは HUD の**バーの下の `VCP_02 · 2 / 6 · 1 moved`** で確認する
   ——モデルが視界の外にあると球の色（黄→緑）が見えず、進んだことに気づけない。
   **触るのは実物ではなくスプラット**（ここが最も取り違えやすいので HUD が毎回念を押す）。
4. 直す必要がない点は **A 短押し**（仮置きが無いときは `Skip`）で飛ばす。
   **合っている点を触ると精度が下がるだけ**なので、全点を置き直す必要はない。
   仮置きが無いときの**左トリガー**は 1 つ前の点へ戻る。
5. **B 短押し**（`Revert this`）／**B 長押し**（`Revert all (n)`）でビルド値（Editor で置いた値）
   へ戻せる。
6. **A 長押し**（または `Done editing` / **Y**）で終了。この時点で PC へ座標が送られる。
   最後の点まで来ると `Skip` が淡色になり、HUD が `last point · Y: finish` を出す。

| 表示 | 意味 |
|---|---|
| 黄の球＋`VCP_04`＋**縦の棒** | いま置き直す点。棒は球とラベルを繋ぐ「ピン」で、部屋の反対側からでも拾える |
| **白の球** | **仮置き（未確定）**。A を押すまで記録されない |
| シアンの球 | まだ触っていない点 |
| 緑の球 | 置き直した点（**確定済み**）|
| 赤の球 | 仮座標のままに見える点（原点付近・0.1 刻み）|
| **灰の点＋`VCP_04 (old)`** | **その点の元の位置**。どれだけ動かしたかが見える |

> **位置合わせ済みだと編集できません（仕様）。** `HasAcceptedSim3` か `Locked` の状態では
> `Edit Virtual CP` が押せず、編集中に自動アラインが通った場合はその場で編集を打ち切ります。
> オーバーレイが実物に重なって見えている状態で Virtual CP を動かすと、無意識に「実物の位置」へ
> 寄せてしまい、**誤差が 0 側にバイアスする**ためです（答えを見ながら定規を合わせるのと同じ）。
> 直したくなったら B で姿勢をリセットしてから。

> **編集すると Real CP は無効化されます。** PC 側の解析は Virtual CP を `cp_survey` イベントに
> 載ったスナップショットから読むので（`experiment_report.py`）、測定後にモデル側を動かすと
> シーンと PC の値が黙って食い違います。だから編集したら測り直しになります
> ——**編集は Real CP の測定より前に済ませること**。

**Editor へ戻す（実験のあと）**: 終了時に PC の `server/received/controlpoints_<modelId>.json`
が書かれる（端末側 `persistentDataPath` にも冗長化のため書く）。Unity の
`Tools > VPTAligned3DGS > Control Points` →「JSON を読み込んで反映」で取り込めば、
シーンに恒久化されて次のビルドから有効になる。**取り込みは必ずこの明示操作を通す**
（実機が自動でシーンを書き換えることはなく、「ビルドしたシーンが正」は保たれる）。
取り込みを忘れた場合、次回起動時はまた Editor の値に戻る（HUD の `▲ Virtual CP edited n` はその注意喚起）。

3. **Real CP の測定（セッションごとに毎回・実機で 1 回）**

   先端校正が終わってから行う（未校正だと HUD が `Cannot set Real CPs yet` で止める）。

   0. **アバターを非表示にしておく**（`Avatar` の `AvatarVisibility` → Show Avatar のチェックを外す）。
      仮想の腕が実際の腕に重なると接触点が隠れ、狙いが甘くなる（→ §5-1b）。
   1. **A ボタン**（または HUD の `Set Real CP`）で開始。HUD が**紫**の
      `SET REAL CONTROL POINTS` になり、**スプラットが自動で消える**（ここで見るべきは実環境だけで、
      位置合わせ前のスプラットは先端を当てたい実物そのものを覆い隠す → §5-3）。
      **球・ラベル・橙の点は消えない**ので「次はどの点か」の案内は残る。どのモデル特徴だったか
      確かめたくなったら X で覗く。
   2. **スティックで CP の球を視界に入れる**。位置合わせ前の球は壁の向こうや天井裏に
      出ていて近寄れないので、まずシーンごと引き寄せる。割当は §5-1 と同じ（右=水平移動 /
      左=上下・ヨー / 押込=呼び寄せ・水平化）。**トリガーはスケールではなく仮置き・取り消し**。
      **球を実物にぴったり重ねようとしないこと** — 用途は「いま何番の点か」を見えるようにする
      ことだけで、重ねると先端が球に釣られて実物からずれ、それがそのままグラウンドトゥルースの
      誤差になる。HUD も `The yellow VCP sphere only says which point — it is NOT on the real object`
      と念を押す。
   3. 指示された CP（`Walk to RCP_01`）の**実物まで歩いて行き**、その特徴点に**先端**を
      当てて**右トリガー**＝**仮置き**。短い振動が返り、当てた位置に**白い点**（`RCP_01 ?`）が
      残る。**この時点ではまだ記録されていない**（HUD が `Confirm RCP_01?` に変わる）。
   4. 白い点を**別の角度から見て**、狙った特徴の上に載っているか確かめる。ずれていたら
      **右トリガーで置き直す**（何度でも）。取り消すなら**左トリガー**。
   5. 納得したら **A 短押し**（`Confirm`）で**確定**。ここで初めて記録され、白い点が
      **橙の点**に変わって次の点へ進む。
   6. 6 点すべて終わると自動で完了し、`Real CP set: 6 points (#1)` になる。以降の**全試行でこの値を使う**。
   7. 確定済みの点を測り直したいときは**左トリガー**（仮置きが無い状態）で 1 つ前に戻る。
      中断は **Y**（または `Cancel`）——**A では中断しない**（A は確定に取られている）。

   **見えるもの**:

   | 表示 | 意味 |
   |---|---|
   | 黄の球＋`VCP_03`＋**縦の棒** | いま触る点の **Virtual CP**（Editor で置いた位置）。**実物の位置ではない** |
   | シアンの球 | まだ測っていない点 |
   | 緑の球 | 測り終えた点 |
   | **白い点＋`RCP_03 ?`** | **仮置き（未確定）**。A を押すまで記録されない |
   | **橙の点＋`RCP_03`** | **確定した Real CP**（実際のワールド座標）。当てた場所に残る |

   **ラベルの頭文字で見分けます**（`V`=モデル上の球 / `R`=実測した点）。同じ点の 2 つの側が
   すぐ隣に並ぶので、色だけを頼りにしないで済むようにしてあります。
   橙の点と球のズレが、その時点での位置合わせ誤差そのものです（測定中は手で寄せただけなので
   大きくてかまいません）。左トリガーで戻ると、その点の橙は消えます。

   > **球・ラベル・点は「見かけの大きさ」を一定に保ちます**（`CpGizmos`）。実寸固定だと
   > 先端を当てる距離ではちょうどよくても、CP は部屋じゅうに散らばっていて実際には 3m 前後
   > 離れて探すことになり、その距離では球は **0.5°（10px 前後）**・文字は判読不能になって
   > スプラットの背景に埋もれます。実機で「CP_01 だけ見えて CP_02〜06 が見えない」と
   > 報告されたのがこれで、6 点とも描画はされていました。**1m 以内は実寸（球は直径 5cm）**
   > なので、当てるときの精度は変わりません。

   > **球はあくまで目印で、記録される値には一切影響しません。** 記録するのはコントローラ先端の
   > ワールド座標だけなので、シーンをどこへ動かしていても、どの実物を CP_01 として置いたかさえ
   > 分かれば測定は成立します（球はその対応を思い出すための補助）。

   | 弾かれる操作 | 何が起きるか |
   |---|---|
   | 先端が未校正のまま右トリガー | 仮置きしない。琥珀で `Controller tip is not calibrated` |
   | 前の点からほとんど動いていない | 仮置きしない。振動 2 回＋`Tip has not moved (3 cm since the last point)`（判定は**仮置きの時点**で、比較相手は**確定済み**の前の点。同じ点を何度置き直しても結果は変わらない）|
   | 仮置きしていないのに A | 記録しない。振動 2 回＋`Nothing to confirm — touch the point and pull the right trigger first` |
   | 途中で試行を始めようとする | 開始ボタンが淡色。全点を測り終えるまで試行は始められない |

   > 2 つ目のゲートは、**誤差の大小ではなく「動いたかどうか」だけ**を見ています。
   > 誤差で弾くと測定結果に都合よくバイアスがかかりますが、移動量は測定対象と独立です。

   > **測定後に原点が動いたら測り直し。** 再センタリング・ヘッドセットの着脱・トラッキング喪失を
   > 検出すると Real CP は無効化され、HUD が `… — set them again with [A]` に変わります。
   > 試行の途中なら、その試行も破棄されます（→ §7-5）。

### 9-2. 試行の回し方（10 試行）

1. §5 の通り `run.py` と `localize` を起動しておく（**試行ごとの再起動は不要**）。
2. 9-1 の準備を済ませ、HUD が**青**（試行を開始できます）になっているのを確認。
   琥珀なら指示文に不足項目が出る（`Set the Real CPs once — [A]` など）。
3. **B ボタン**（または HUD の `Start trial`）を押す。内部では次が一括で走る:
   自動送信停止 → PC へ RESET（新 session フォルダ＋CV の蓄積破棄）→ Quest 側の状態初期化（採用済み Sim(3)・splat 姿勢・送信カウンタ・アンカー）→ 計測開始 → 自動送信 ON。
   **Real CP はここでは触らない**（試行をまたいで使い回すため）。
4. HUD が**青緑**「部屋を見回してください」に変わり、3DGS が消える。**少し横方向に動きながら**
   部屋を歩き回る（並進が無いと相似変換が悪条件になる）。バーに残り秒数が出る。
5. 所定時間（既定 60 秒）で収集終了。**試行に成否はありません** — 曲線は保存済みキーフレームから
   後で引くので、その場で確定に至らなくてもデータは使えます。姿勢が適用されていれば
   3DGS が出るので、目視で確認できる（X で消して見比べられる）。
6. **B ボタン**で次の試行へ。これを 10 回繰り返す。

### 9-3. 主結果: 収集時間と精度の関係

**評価の主結果は「何秒データを集めたら、どれくらい合うか」の曲線**です。
ロックまでの時間は品質ゲートの閾値の関数でしかなく、閾値を変えると数字も変わってしまうため、
手法の性質を測る指標としては使いません。

仕組み上、**1 回の歩行データから曲線全体をオフラインで再構成できます**。
`localize.watch` が各キーフレームのローカライズ結果を `kf_localized.jsonl` に保存するので、
「最初の t 秒分だけで Sim(3) を解き直す」を t を変えて繰り返せばよく、hloc の再実行は要りません。

誤差の定義に循環はありません。コントロールポイントは 2 つの独立した座標を持ちます。

- **Virtual CP**（ログの `local`）… 3DGS モデル上に定義した座標（アラインに依存しない）
- **Real CP**（ログの `tip`）… 校正済みコントローラ先端で実測した物理位置（ワールド座標）

候補変換 `T` の誤差は `|T(Virtual CP) − Real CP|`。どちらも `T` の推定に使っていないので
評価として成立します（写真測量の用語では、推定に使わないこの 6 点は control point ではなく
**check point（検証点）**にあたります）。

**全試行をまとめる（論文の図はこれ）**

```powershell
python analysis\experiment_report.py --received received
```

**`adb pull` は要りません。** Real CP など解析に必要な行は、計測した時点で Quest から
UDP（type=7）で PC へ送られます（PONG の `ev_ack` で受領確認し、未達分は Quest が再送）。
HUD の右下に未送達件数が出るので、**0 になってからヘッドセットを外してください**。

保存先は 2 か所です。

| 場所 | 中身 |
|---|---|
| `received/quest_events.jsonl` | 正本。到着順に全イベント（**Real CP の測定はここだけ**） |
| `received/session_*/quest_events.jsonl` | その試行ぶんの複製。セッションを開けばキーフレームと経過がまとまって見える |

複製の振り分けは**到着時刻ではなく行に載っている試行ラベル**で行うので、試行が終わった後に
再送で届いた行も正しいフォルダに入ります（到着時刻で振り分けると次の試行に紛れ込む）。
Real CP の測定は実験前に 1 回きりでどの試行にも属さない（`trial=0`）ため、複製はされず正本にだけ載ります。
どの試行がどの測定結果を使ったかは `trial_start` の `survey` が持っています。
解析はどちらを読んでも同じで、`(run, seq)` で重複除去されます。

端末内の JSONL は冗長化として残してあります。両方を突き合わせたいときは:

```powershell
adb pull /sdcard/Android/data/com.DefaultCompany.VPTAligned3DGS/files/experiments/ .\logs\
python analysis\experiment_report.py --received received --logs received\quest_events.jsonl .\logs
```

行は `(run, seq)` で重複除去されるので、両方に同じ行が入っていても二重に数えません。

セッションと試行はラベル（`trial-01` …）で自動対応。中断・原点移動・Real CP 未測定の試行は
理由つきで除外されます。出力は `curve_aggregate.png`（中央値＋四分位帯）/ `curve_aggregate.csv` /
`curve_per_trial.csv` と、標準出力の表（採否一覧・時間 vs 誤差・試行ごとの最終値・**試行間の再現性**）。

> 曲線の右端は**いちばん長い試行**に合わせます。短い試行に合わせて切ると 60 秒分の
> データの大半を捨てることになるため。各時点で「そこまで歩いていた試行数」を併記します。

**1 試行だけ詳しく見る**

```powershell
python analysis\accuracy_vs_time.py received\session_<時刻> logs\exp_<時刻>.jsonl --trial <番号>
```

> **Real CP の測定と全試行は同じアプリ起動の中で行うこと。** ワールド原点が変わると
> キーフレーム姿勢と Real CP を突き合わせられません（測定値は自動で無効化されます → 9-1 の 3）。

出力: `accuracy_vs_time.csv` / `accuracy_vs_time.png`、および標準出力に
「最初に解けた時点」「中央値 10cm / 5cm に到達した時点（時間と歩行距離）」「最終誤差」。

**試行間の再現性について**: `experiment_report.py` は「独立な試行が同じ姿勢に収束したか」も出します。
これは CP 誤差とは独立した主張になる強い結果ですが、**同じワールド座標系のグループ内でしか
比較できません**（試行の合間に原点が動くと、比較しているのは手法の再現性ではなく
「原点が回った角度」になる）。グループの切れ目はスクリプトが自動で検出します。

### 9-4. Real CP と収束の健全性チェック（Table 1 の枠）

```powershell
adb pull /sdcard/Android/data/<パッケージ名>/files/experiments/ .\logs\
cd C:\Users\heatf\Desktop\VPTAligned3DGS\server
python analysis\analyze_experiments.py .\logs\ --outdir analysis_out
```

出力: 標準出力の要約（Real CP の健全性、先端校正のばらつき、Virtual CP の VR 編集、コールドスタート収束の成功率・時間・KF 数）、
`cp_survey.csv` / `tip_calibrations.csv` / `trials.csv` / `model_cp_edits.csv` / **`table1.tex`（論文の表の枠）** / `survey_check.png`。

> **オーバーレイ精度（Table 1 の該当行）はこのスクリプトからは出ません。** Real CP の測定は実験前に
> 1 回だけなので、そのとき記録される誤差は「測った瞬間に適用されていた姿勢」に対する
> 見かけの値でしかなく、どの試行の精度でもありません。論文の数値は 9-3 の
> `experiment_report.py`（保存済みキーフレームから試行ごとに姿勢を解き直す）から取り、
> `table1.tex` の `X.X` を手で埋めてください。

警告が出る条件（いずれも測定の妥当性に関わる）:

- 先端未校正のまま記録された Real CP がある → その測定値は論文に使えない
- 前回セッションの校正値を流用した Real CP がある（`tip_source="Restored"`）
- 校正の前回値との差が 5mm を超えた → コントローラや治具の取り違えを疑う
- **位置合わせ済みの状態で Virtual CP を編集した**（`aligned=true`）→ 誤差が 0 側にバイアスして
  いる可能性があり、**そのログの精度は報告に使えない**（本来ブロックされる。出たら経緯を確認する）
- **Real CP を測ったあとに Virtual CP を編集して測り直していない** → シーンの値と PC 側の `local` が
  食い違う（→ 9-1 の 2b）
- **Real CP の測定が 2 回以上ある** → 途中でワールド原点が動いた可能性。どの試行がどちらを使ったかは
  `trial_start.survey` で分かる（`experiment_report.py` の一覧の「測量」列）

**点ごとの内訳を必ず見ること。** 1 点だけ誤差が大きい場合、それはシステムの精度ではなく
その CP の対応がずれている（Virtual CP の置き場所か、実物の指し先）可能性が高い。
Real CP の測定は 1 回きりで**全試行が道連れになる**ので、疑わしければ測り直す（A ボタン → 9-1 の 3）。

### 9-5. 記録されるログ

`Application.persistentDataPath/experiments/exp_<時刻>.jsonl`。1 行 1 イベントで、全行に試行番号 `trial` が付く（試行外は `trial=0`）。

| type | 意味 |
|---|---|
| `trial_start` / `trial_end` | 試行の区切り。`trial_start` に使った Real CP の測定番号 `survey`、`trial_end` に `verdict`・`time_to_lock_s`・`kf_at_lock` |
| `kf_sent` | キーフレーム送信（`req` は試行内の連番） |
| `sim3_received` / `sim3_gate` | PC からの解の受信と、Quest 側ゲートの採否 |
| `auto_aligned` | **自動**位置合わせが成立した瞬間（収束点。手動 Lock とは別物） |
| `cp_survey_start` / `cp_survey` / `cp_survey_done` | 実験前の **Real CP** の測定（`trial=0`）。`cp_survey` が 1 点ぶんの実測（`tip`＋そのときの `local` のスナップショット）|
| `cp_survey_cancel` / `cp_survey_invalidated` | 測定の中断と、原点移動による無効化（理由つき） |
| `cp_model_edit` | **Virtual CP** の VR 編集（`action`=start/place/end）。`place` に移動量 `moved_m` と `aligned` が付く |
| `cp_model_edit_revert` / `cp_model_point` / `cp_model_edit_done` | ビルド値へ戻した／編集後の全点の座標／編集の締め。後 2 者から PC が `received/controlpoints_<modelId>.json` を書く |
| `tip_calib_done` / `tip_calib_fail` | 先端校正の結果（オフセット・残差・向きの広がり・前回値との差 `drift_mm`） |
| `tip_calib_reused` | 前回セッションの校正値を明示的に流用した（該当する Real CP は `tip_source="Restored"`）|
| `tracking_origin_changed` | ワールド原点の移動を検出（Real CP の無効化・試行の破棄の根拠） |
| `scene_info` | スプラット数 |
